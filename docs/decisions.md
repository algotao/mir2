## 0. 第一优先：美术资产缺失（D-15）

### 0.1 实测：`$WS/mir2.exe` 是登录器，**不含**美术（2026-10-07）

`$WS/mir2.exe`（129,739,520 字节，PE32）**不是游戏客户端**，而是**盛大登录器**。
7-Zip 对它自动识别失败（自定义 SFX stub），但**偏移 `40,876,032`（0x26FB000）处内嵌一个 7z 归档**：

```bash
tail -c +40876033 mir2.exe > payload.7z    # 从 7z 魔数(37 7A BC AF 27 1C)偏移切出
7zz x -o./sfx payload.7z
```

解出 21 个条目，**全部是启动器模块**：`Legend.exe`（29 MB 启动器）、`LaunchLegend*.update` ×11
（PE DLL 模块）、`MyMirLoader*.update`、`Legend_MirOld.update`、`Launch100m_b.dll`、
`v1.avi`（26 MB 开场视频）、`Legend.ini` / `LegendCfg.ini`。

- **无任何 `.wil` / `.wix`**；`Legend.exe` 的 PE 资源只有 Delphi VCL 自带位图（`BBABORT.bmp` 等）。
- `Legend.ini` 的 `[Download] Dir=` **为空**、`[WilImage]` 段为空 ⇒ 登录器尚未配置客户端下载源。

⇒ **不解决 D-15。** 需要的是**游戏客户端目录本体**（含 `Data/*.wil`、`Graphics/*.wil`、`Wav/`、`Music/`），
而不是登录器。素材来源仍需你裁决（自有副本 / 购买 / 其它来源）。

## D-01 技术栈

**状态：已定。**

| 端 | 选型 | 理由 |
|---|---|---|
| server | **Go** | 从 `mir2go`（63,867 行）抽取领域层，省掉最大的重复劳动 |
| client | **Rust + SDL3** | exe 3–5 MB、运行期零依赖、Win/mac 一套代码 |

客户端依赖清单（就这些，全部静态编进去）：

- `sdl3`——窗口 / 输入 / 音频 / 计时 / 线程
- `softbuffer` 或 SDL3 `gpu`——上屏（见 D-07）
- `prost` / `prost-build`——协议代码生成（见 D-12）
- `minimp3-rs` + 自写 WAV 解析——音频
- 字体：**自带点阵字库**（原版本身就是位图字库），零字体依赖

构建参数（体积）：`opt-level="z"`、`lto="fat"`、`codegen-units=1`、`panic="abort"`、
`strip=true`、Windows 加 `+crt-static`。

## D-02 全栈 UTF-8，弃 GBK

**状态：已定。**

**协议自由后，本条从"三个后果要处理"简化成"一条规矩"**：

> 协议层只搬字节；rune 安全的截断/换行只在 UI 层做。

原先因 Delphi `String[N]`（字节口径）而产生的三个后果——**字节容量预算、`EqualFold` 比较语义、
排序口径——全部作废**（不再有定长字节名字段）。

**转码只发生在边界**：

- `mir2go` 侧运行期唯一转码点 `internal/castle/sabuk.go:336 decodeGBK` 必须下沉到导入工具。
- 新 `mir2` 服务端**不允许**出现任何运行期字符集转码。
- 所有 loader 加 `utf8.Valid` 断言：非法即启动失败，不要静默乱码。

**遗留数据导入**：`mir2standard` 的配置、`mir2go` 的 `data/` 都是 GBK 或混合编码，
在**导入那一刻**转成 UTF-8，之后全链路 UTF-8。

## D-03 文件名全小写、无中文、`/` 分隔

**状态：已定。**

**依据**：一次性消灭三个跨平台坑（大小写敏感文件系统、GBK 文件名、反斜杠）。
macOS 默认大小写不敏感，会**掩盖**大小写 bug——由本条一次性消灭。

**新项目是"自己的资产树"，可以完全自己定义**（不再被原版文件名绑架）：

- 资产树由 `tools/` 从 `mir2standard` / `Mir2-GeeM2` **生成**，命名规则自己定。
- 若沿用原版文件名（`Data/Hum.wil` 等），需做规范化：`data/` 侧实测 **855 个大写名 +
  324 个非 ASCII 名**（分布见 [legacy-analysis.md §7](./legacy-analysis.md)）。
- `data/monitems/*.txt`（300 个中文名）**文件名即怪物名**——不要重命名，
  改为索引文件，摆脱"文件名当数据主键"的耦合。

**做法**：一次性 `tools/assetnorm`，产出并提交 `normalize.manifest`（原路径 → 新路径 +
冲突检测）。**不要手工 rename**：

- 仅大小写不同的两个文件在 macOS 上无法共存，而 git 在 mac 上通常
  `core.ignorecase=true`，会**静默忽略纯大小写改名** → 必须两步 `git mv a tmp && git mv tmp A`。
- 规范化若牵动 JSON key，需同步验证数据导出工具的逐字节复现约束。

**收尾**：加门禁，发现大写或非 ASCII 路径即报错。

## D-04 平台目标：Windows 发布 + macOS（M4）体验 + Linux 只跑 headless e2e

**状态：已定。**

| 平台 | 角色 | 要求 |
|---|---|---|
| **Windows** | **发布目标** | 单 exe + 资产目录，零运行期依赖（C-7） |
| **macOS / Apple Silicon（M4）** | **用户体验端**（开发期的主要体验机） | 能直接跑；target `aarch64-apple-darwin` |
| Linux / 容器（**可选**） | 只跑 headless 的 e2e 产物，不跑 GUI | 无显示 / 无音频设备（见 D-18） |

**不做**：`.app` bundle、universal2、codesign / notarize、双架构分发（现阶段）。

**代价（反而要求更高）**：mac 会掩盖大小写 bug（D-03 已消灭）；
路径统一 `/`；UTF-8 无 BOM。

**SDL3 在 macOS 的依赖形态 —— 已核实（2026-10-07）**

`sdl3` crate（0.20.x）**默认不启用任何 feature**；自带源码构建与静态链接由这些 feature 提供：

| feature | 行为 |
|---|---|
| `build-from-source` | 从源码编译 SDL3（动态链接） |
| **`build-from-source-static`** | **从源码编译并静态链接** ← 采用这个 |
| `static-link` | 链接**系统已有的**静态 SDL3（仍需先装 SDL3） |
| `use-pkg-config` / `use-vcpkg` | 查找系统库 |
| `link-framework` | macOS Framework 形式的 SDL3 |

⇒ 采用 **`build-from-source-static`**：SDL3 源码随 crate 一起编进我们的二进制，
**C-7「零运行期依赖」在 Mac 上成立**（SDL3 是 zlib 许可，允许静态链接），
也**不需要** `brew install sdl3`。

**构建期**需要的额外工具：C 编译器（macOS 上 Xcode Command Line Tools 自带 clang）
与 **CMake**。⚠️ 这是**构建期**依赖，**不违反 C-7**（C-7 说的是运行期）。
首次编译 SDL3 要几分钟，之后走 cargo 缓存。

**落地验证（2026-10-07，macOS M4 Pro）**：CMake 4.4 + Apple clang 21 构建通过。
另核实：**SDL3 源码由 `sdl3-src` crate 一并下发**（vendored），**不依赖构建期从 GitHub 实时下载**——
即构建只依赖 crates.io（配好镜像即可），无额外网络风险。

**R-9 因此关闭**；D-01 不需要重新审视。

另：macOS 上的**中文输入法**与原版 Windows IME 不等价，属"体感抽查"项，不在 M1 承诺。

## D-05 协议自研，不兼容原版报文

**状态：已定（取代原 `mir2client` 的 D-05「沿用遗留字节协议」）。**

**依据**：两端都在自己手里，不再需要兼容原版客户端；原版报文（6bit 码表、
`#<1-9>…!` 字符帧、`TDefaultMessage` 12B + 16 位 `Series`、Delphi `String[N]`、
`DEFBLOCKSIZE=16`、`*/$S/$R`）没有任何保留价值。

**删除的东西**（连带消灭的坑）：

| 原约束 | 现状 |
|---|---|
| `String[N]` 字节容量、中文 2→3 字节缩水 | **消失** |
| `EqualFold` vs `CompareText` 语义差、名字白名单 | **消失** |
| 排序口径（字节序 ≠ 拼音序） | **消失** |
| `codec.PutShortString` 的 `b[:n]` 切坏多字节 | **消失**（风险点蒸发） |
| `TDefaultMessage.Series` 16 位装不下 `ActorId`、必须坐标优先定位 | **消失** |
| 6bit 码表、`#<1-9>…!` 帧、`DEFBLOCKSIZE`、`*/$S/$R` | **全部删除** |

**代价**：`mir2go` 的 46/46 e2e 与 `mir2cli` **不能直接复用**（它们是围绕遗留协议建的）。
它们转而作为 **mir2go 参照系统自身的回归**，不再服务于新项目。

**新增的最大风险**：见 [protocol.md §9](./protocol.md)——**双实现漂移**。

## D-06 美术"同一套、载体自选"

**状态：已定（放宽自原 `mir2client` 的"原格式直读，不转码"）。**

**依据**：体感一致 ⇒ 必须同一套美术；但**载体属于技术实现，可以自由选**。

载体方案见 [assets.md](./assets.md)，决策见 D-11。

## D-07 渲染：先 CPU 软件合成，后可选换 GPU

**状态：待定。** 推荐先 CPU。

**依据**：原版本来就是软件混合（`DXRender.pas` 8,081 行，含 JIT 代码生成）。
800×600 = 48 万像素，现代 CPU 完全够，且 CPU 合成**行为天然与原版一致**，零 GPU 兼容风险。
先把"走路 + 打怪"跑通，再按实际观感需求局部替换为 SDL3 GPU。

**约束**：渲染接口边界要在 M1 就设计好，保证后续替换不触碰上层。

**⚠️ 附带约束（体感）**：可以提高分辨率，但**视野格数必须锁死**。
原版视距是玩法平衡的一部分，看得更远 = 更容易。

## D-08 排期单位用「验收点/天」

**状态：已定。** 速率基准 **2–3 验收点/天**。

**依据**：行数指标有四个结构性问题：

1. 诱导写"多行但简单"的代码。照搬 70 个手写动画类能刷出 7.6k 行，
   而一个引擎 + 数据表只要 5k 行 —— **前者行数好看，后者才是对的**。
2. **删除不计入产能**。删掉 46k 行 DirectX 包装在行数上是负数。
3. **评审吞吐是隐形上限**。3K 行/天等于零深度评审，缺陷后移，
   在无自动化验收处（手感、时序、遮挡）以 10 倍代价偿还。
4. 对"移植遗留"不成立——搬迁要先读懂 87k 行 Delphi。

## D-09 验收 = 两端契约测试 + 体感抽查

**状态：已定（取代原"以原版对拍为验收标准"）。**

**依据**：协议自研 ⇒ 一致性不再由"原版客户端能否连上"来判定，而由
**生成的两端实现能否互通**来判定。这是质变：

| | 原（对拍原版） | 现（契约测试） |
|---|---|---|
| 判定者 | **人眼**看截图/抓包 | **自动断言** |
| 覆盖 | 抽样 | 全消息 |
| 回归成本 | 每次手工 | CI |

> ⚠️ **"美术直读"这一行已被 D-31 取代**（2026-10-08）：美术现在是
> `assets/image/images.m2pk`（kind=3，**每 32 张一组拼接**），实测 1776 → 1346 MB。
> 注意 D-11 下面那句"全量 M2PK（每项独立压缩）体积 ≈ 现状"**依然成立** ——
> 有效的是**按组拼接**（跨图共享上下文），不是"再压一遍"。

**保留的硬要求**：**地图**转换必须提供 `verify`（D-06）——逐格比对。

**被否掉的两个方案**
- **全量 M2PK（每项独立压缩）**：体积 ≈ 现状，纯亏工具链 ⇒ 否。
- **全量 M2PK（分块 solid）**：美术可再省 ~300 MB，但要换"转换器 + verify + 块缓存 + 素材更新重跑" ⇒
  收益/成本不如直读 ⇒ 否（**保留为日后可选优化**，不影响架构）。

**代价**：客户端内置 ~200 行 WZL/WZX 读取器 —— 可接受。

**落地（2026-10-07）**：地图容器已实现 ⇒ [`internal/m2pk`](../internal/m2pk) + [`tools/m2pk`](../tools/m2pk)。
`$WS/mir2c/map` **770 张 / 253.73 MB → 8.83 MB（比率 0.0347，−96.5%）**，
`verify` **逐字节**回验通过（D-06 硬要求）。

**对上面括注的两处修正**（决策本体不变：地图仍走自研容器）：

1. **"分块 solid" 不值得**。全量 solid 相对"一图一块"只省 **6.5%**（zstd：7.7 → 7.2 MB），

2. **编码器改用 brotli q11，不是 zstd**（详见 [assets.md §5.4](./assets.md)）：
   纯 Go 的 zstd（klauspost）比 libzstd 的高档位**差 56%**，先用它实现时容器是 14.46 MB；
   换 brotli 后 8.83 MB。两端都有成熟**纯**实现（Go `andybalholm/brotli`、Rust `brotli`），
   不引入 cgo / C 依赖（符合 D-21）。

## D-13 连接 / 进程 / 服务器边界

**状态：待定。** 推荐：**客户端单连接；服务端三个逻辑角色；横向扩容靠"多区组 + 无状态 gate"。**

### 0. 先把三个轴拆开

原版把它们绑在一起了，这是复杂度的根源：

| 轴 | 决定因素 | 原版 |
|---|---|---|
| **进程边界** | 故障域、生命周期、**写所有权** | 7 个进程 |
| **连接边界**（客户端几条 TCP） | 鉴权边界、故障切换、网络路径 | 3 条（Login/Sel/RunGate） |
| **服务器边界**（几台机器） | 容量、地域 | 一个区组多台 |

原版把**服务器边界**的需求（一台机器扛不住连接数）**泄漏进了连接边界**（客户端必须换连接），
于是不得不发明 ticket、跨连接会话迁移、三套客户端状态机。

### 1. 账号 DB 与游戏数据分开 —— 必需，但它要求的是"写所有权"，不是"多连接"

规则：

| 数据 | 唯一 writer |
|---|---|
| `accounts` | **只有 `accountsvc`** |
| `characters` | **只有持有该角色租约的 `gamesvr`** |
| `guilds` / 城堡 / 全区共享状态 | 该区组的 `gamesvr`（`mir2go` 已如此） |

为什么必须分开：

1. **同一角色必须被单一进程独占写**，否则两个区组同时改一个角色 = 装备互相覆盖
   （原版的经典 bug 家族）。
2. 账号是**跨区组共享**的（一个账号在多个区组都有角色），所以它的 owner **不能是任何单个
   `gamesvr`**。
3. 生命周期不同：账号库长期持久；游戏内存状态易失，进程随时可重启。

⇒ **进程必须分开、数据必须分离**，但边界是"**写所有权 + 租约**"，与客户端开几条 TCP **无关**。

### 2. "先选后进入" —— 是状态机阶段，不是连接阶段

| 阶段 | 需要什么 | 由谁提供 |
|---|---|---|
| 握手 | 协议版本、能力协商 | 连接的终结者 |
| 认证 | 账号库 | `accountsvc` |
| 列角色 | 该账号在本区组的角色 | `accountsvc` |
| **选角** | **申请角色租约（独占权）** | `accountsvc`（仲裁者） |
| 加载角色档 | 角色档、物品、技能 | `gamesvr` |
| 进世界 | 地图、实体、广播 | `gamesvr` |

**关键**："先选后进入"的本质是"**进入世界之前必须独占该角色**"，原始需求是防双开覆盖。
它要求的是**跨进程的租约仲裁**，**不是**客户端的两条连接。

`mir2go` 已实现过这套：`game_tickets`（一次性票据，不可重放）+ `game_leases`
（主键 `(account, character_name)`：同角色互斥、同账号多角色可并行）。**可原样搬过来。**

### 3. 推荐拓扑

客户端视角：**一条 TCP、一个地址、一个状态机**。

```
客户端（单 TCP，只连"区组地址"）
  → [gate]     无状态：接入 + 4B 分帧字节转发 + 按连接限流 + 连接元数据
  → [gamesvr]  该区组的会话状态机
        ├── 内部 RPC → accountsvc：认证 / 角色列表 / 申请·续租·释放租约
        └── 本地：加载角色档 → 进世界 → 数据面
```

- **`gamesvr` 是客户端的唯一对端**；账号能力走**内部 RPC**（gRPC），
  **`accountsvc` 不对客户端 Listen**。
- 于是：不需要"连接迁移"，也不需要把 ticket 传给客户端
  （租约在 `gamesvr` 内直接申请）。
- 账号库的写天然串行（只有一个 writer）。

**为什么不让 `accountsvc` 直接面对客户端**（原版做法 / 双连接方案）？
那会让"选角完成 → 进入世界"变成**跨连接/跨进程的状态迁移**，必须发明 ticket 机制桥接——
这正是原版复杂度的来源。双连接的收益是故障隔离，代价是客户端两套状态机、两份心跳、
跨连接会话一致性风险。**在这个项目里不值。**

### 4. "选服"怎么办

原版顺序：连 LoginSrv（账号，跨区）→ 服务器列表 → 选服 → 连该区组 → 选角。
**体感保留，但把灵活性放回它该在的层——数据，而不是连接拓扑：**

- **阶段 1（M1–M2，自用）**：区组列表写在客户端配置里（选服界面渲染本地清单）。
- **阶段 2（若要运营）**：加一个**轻量清单服务**（HTTP GET 一份 JSON：区组名/地址/负载/公告），
  客户端启动拉一次。**这是新增一个独立小服务，不改连接模型。**

### 5. 多程序：三个逻辑角色，建议编译成 1 个二进制

- 三个**逻辑角色**要分开：`gate`（无状态转发）、`accountsvc`（账号 + 租约仲裁）、
  `gamesvr`（区组世界）。理由：写所有权不同、生命周期不同、伸缩方式不同。
- 但**不必是三个二进制**。`mir2go` 已证明 `-role` 多角色可行。
  自用场景 `--role=all` 一个进程最省事，上线时按角色拆开。
- **不要把账号能力塞进 `gamesvr`**——那是上帝对象的老路，会让"角色归属"失去唯一仲裁者。

### 6. 多服务器：部署问题，且有一条硬约束

- **硬约束：一个区组 = 一个 `gamesvr` 进程。** MIR2 的世界状态是**全局共享**的
  （同地图的玩家/怪物/广播/掉落都在一个世界模型里）。**不能把一个区组横向拆成多个
  `gamesvr`**（除非做地图分片，而视野/广播/AI 跨地图边界，投入产出极差）。
- 因此"多服务器"只有三种合法形式：
  1. **多区组** → 多 `gamesvr`（天然分片，账号跨区共享）
  2. **`gate` 多实例** → 无状态，前面挂 LB，**客户端地址不变**
     （这才是原版"多 gate"需求的真正归位之处）
  3. **`accountsvc` 单实例**（早期）；压力大时它只是薄 RPC + DB 层，先垂直扩，
     之后按账号 hash 分片
- **容量判断**：一个区组的真实并发在几百到几千连接量级，Go 单进程轻松扛住
  （epoll，每连接几十 KB/s）。所以**早期 1 个 `gate` 进程足够**——多实例是
  "保留能力、不预先支付复杂度"。

### 7. 三条派生硬要求

1. **会话 token 必须独立于 TCP 连接对象**。否则断线重连与"租约宽限"无法实现
   （断开不立即释放租约，超时才释放）。这是单连接方案能否成立的关键。
2. **租约由 `accountsvc` 唯一仲裁**，`gamesvr` 只是申请方 / 续租方 / 释放方。
3. **`gate` 保持无状态**（[D-17](#d-17-gate-不做协议感知)），上面第 6.2 条依赖它。

### 8. 待拍板

1. 接受"`gamesvr` 作为客户端唯一对端 + 账号走内部 RPC"（替代原版 LoginSrv 直接面对客户端）吗？
2. 选服清单：先写客户端配置，还是现在就要那个轻量清单服务？

## D-16 消息类型用 oneof 信封，字段号即消息号

**状态：已定。** 完整论证见 [protocol.md §4.1](./protocol.md)。

**结论**：**不设独立的 `msg_id` 字段**。用 `Envelope.body` 这个 oneof 的**字段号**
同时承担「类型标识」与「线上编号」两个角色（`field 0x0503 → EntityMove`）。

**收益（按重要性排序）**

1. **编译期穷尽性**：加一条消息，两端**所有分发点都会编译报错**，逼你处理。
   `msg_id` + `bytes body` 给不了这个——加了消息忘了处理会静默走 default 分支。
2. 类型与编号**只有一处定义**，重命名类型不会漏改编号。
3. 日志直接打印变体名，不再是数字。
4. 省掉每包 3–5 字节的 `msg_id`。

**三条硬规则**

- 字段号**全局唯一、永不复用**；避开 protobuf 保留区 **19000–19999**
  （我们的 `0x01xx`–`0x0Cxx` 完全避开）。
- `oneof` 无法跨文件扩展 ⇒ **字段列表集中在 `protocol/envelope.proto`**
  （消息体仍按模块拆文件）。这份集中列表即"消息总目录"。
- 收到未知消息时 oneof 的 case **未设置** ⇒ 显式处理 `None`：记数 + 告警 + 忽略，
  **禁止 panic**。

**反向条件**（何时该改回 `msg_id` + `bytes`）：需要 gate 做协议感知转发 /
消息数膨胀到几百上千 / 需要协议层可被外部扩展（oneof 无法从外部扩展，是唯一硬限制）。
后者的逃生舱是在信封里留一个 `Raw { uint32 msg_id; bytes body; }` 变体给 GM 与调试用，
不必推翻整体设计。

## D-17 gate 不做协议感知

**状态：已定。**

**依据**：原版三个 gate（LoginGate / SelGate / RunGate）各自拆包，是为了注入真实 IP、
按消息限流等；代价是 gate 必须**理解协议**，跟着 schema 一起变。

新协议下让 gate 退化成**纯粹的 TCP 接入层**：

- 只做：连接接入、4 字节长度分帧的**字节转发**、按连接限流、连接元数据采集。
- 真实 IP 等信息走**内部 RPC 的 metadata** 传给 `gamesvr`，不塞进协议报文。
- gate **不需要**有 protobuf 依赖。

**收益**

- gate 不随 schema 演进；`oneof` 需要完整 parse 的代价问题在 gate 侧直接消失
  （[protocol.md §4.1](./protocol.md)）。
- 进程划分更简单：gate 可以是无状态的（甚至用现成的 L4 代理思路）。

**代价**

- 按**消息类型**的限流 / 审计 / 黑名单要放到 `gamesvr`（gate 只能按连接与字节量限流）。
  这属于可接受的迁移成本。

## D-18 客户端是**两个产物**，共用同一个 `core`

**状态：已定。**

| 产物 | 形态 | 运行环境 | 依赖 |
|---|---|---|---|
| `client/e2e` | CLI 程序（读剧本 → 断言 → 退出码） | **无显示环境**（Mac 本地 / 容器 / CI 都能跑） | **禁止依赖 SDL3** |
| `client/app` | GUI 程序 | Windows 发布 / macOS M4 体验 | SDL3 |

两者**共用 `client/core`**：协议编解码、会话状态机、资产解码、配置。

### 为什么 e2e 不许依赖 SDL3

1. e2e 必须能在**无显示环境**里跑（容器 / CI）。即便在 Mac 上跑，也**不该为了测试拉起
   窗口与音频设备**——SDL 在无设备时会初始化失败，靠 dummy driver 绕过去是不该依赖的技巧。
2. 少一个原生依赖：构建更稳、CI 更简单、容器镜像更小。
3. **职责边界本来就不同**：e2e 验证协议与逻辑；渲染与手感属于"体感抽查"（D-09）。

### 最重要的一条纪律

> e2e **必须走与 `app` 完全相同的协议编解码与会话状态机**，
> 不允许任何"测试专用捷径"。否则契约测试形同虚设——它检验的就不是真客户端了。

### 可自动化的门禁（CI 里加一条）

```bash
cargo tree -p mir2-e2e | grep -q sdl3 && { echo "e2e 不许依赖 SDL3"; exit 1; }
```

### 产物 1 能在无显示环境里跑的前提

**不依赖美术库**（D-15 的素材至今缺失）。所以：

- e2e 的第一批剧本只覆盖**协议与逻辑**：登录 / 选角 / 进图 / 移动 / 攻击 / 掉落 / 物品 / 聊天。
- 资产解码用**签入仓库的合成测试资源**（体积小、确定性）验证。
- ⇒ e2e **完全不被 D-15 阻塞**，这也是 M1 能在素材到位前推进的原因。

### 已定（2026-10-07）

**Linux 侧产物出两种架构：`linux/amd64` + `linux/arm64`；默认/首选 `linux/amd64`。**

| 产物 | 目标 | 理由 |
|---|---|---|
| `server`（Go） | **amd64 + arm64** | D-21 无 cgo ⇒ 纯交叉编译，两种架构各一条命令，成本几乎为零 |
| `client/e2e`（Linux） | 容器 / CI 内按宿主架构 | 只跑 headless 契约测试，无需双架构 |
| `client/app`（Windows） | `x86_64-pc-windows-gnu` | 见 D-19 |

**默认 `linux/amd64`**：与 `mir2go` 的现有镜像/部署保持一致，避免"本地 arm64 通过、线上 amd64 挂"。

⚠️ 因此**容器里跑 CI 时要显式 `--platform linux/amd64`**（Mac M4 上 Docker 默认是 arm64）。
这同时消除了 [D-20](#d-20-大小写敏感门禁mac-开发特有) 里"CI 门禁架构与部署架构不一致"的隐患。

## D-19 构建矩阵：**全部原生在 macOS 上开发与构建**

**状态：已定。**（取代原"docker 为主构建环境"的写法）

**前提**：主力开发机 = macOS（Apple Silicon / M4），**不再用容器做日常开发**。

| 产物 | **构建** | 运行 |
|---|---|---|
| `server`（Go） | **Mac 原生**（`CGO_ENABLED=0`） | Mac 本地 / Linux 部署（交叉编译产物） |
| `client/e2e`（Rust） | **Mac 原生** | Mac 本地（亦可在容器 / CI 里跑，见 D-18） |
| `client/app`（macOS） | **Mac 原生** | macOS M4 体验 |
| `client/app`（Windows 发布） | **Mac 原生交叉编译**（`x86_64-pc-windows-gnu` + mingw-w64 + CMake） | Windows |

### 为什么 macOS 产物必须在 macOS 上构建

这条即使容器方案不变也成立：

1. macOS 二进制必须链接 **Apple 的 SDK 与系统框架**（libSystem、CoreFoundation、
   Cocoa/Metal——SDL3 在 mac 上要用到）。交叉编译到 `aarch64-apple-darwin`
   需要 macOS SDK 与 `ld64`，Linux 上没有。
2. 唯一绕法是 **`osxcross`**（把 Apple SDK 塞进 Linux 容器），但：
   **Apple SDK 的许可不允许再分发**；每次 SDK 升级都要重搭；
   **Apple Silicon 上任何可执行文件至少要 ad-hoc 签名**，签名要用 Apple 的 `codesign`，
   `osxcross` 做不了这一步，硬做也很脆。
3. 即便勉强跑通，迭代体验极差：改一行要等交叉编译 + 手工签名 + 拷回 Mac。

### 容器 / CI 的角色降级为可选

- 只用于 **① Linux 部署产物的可复现构建 ② CI 门禁**（尤其是大小写敏感检查，见 D-20）。
- 日常开发**不需要**容器：Mac + Go + Rust + CMake 是自足的。

### Mac 上的交叉编译能力（一条命令出目标产物）

```bash
# Linux 部署产物（纯 Go 才这么轻松，见 D-21）
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build ./server/...
# Windows 发布产物
rustup target add x86_64-pc-windows-gnu
```

## D-20 大小写敏感门禁（Mac 开发特有）

**状态：已定。**

**问题**：macOS 文件系统默认**大小写不敏感**。开发机换成 Mac 之后，
"大小写 bug 被掩盖"从理论风险变成 **100% 的日常现实**——
代码里的 import 路径、引用的资源名、`.proto` 文件名，写错了在 Mac 上照样跑，
**部署到 Linux 才炸**。

**这是 [D-03](#d-03-文件名全小写无中文--分隔) 的互补措施**：
D-03（全小写命名）**减少风险面**，D-20 **兜住剩下的**（代码/配置里的引用大小写）。

**对策（组合，全部落实）**

| # | 措施 | 说明 |
|---|---|---|
| 1 | **用大小写敏感的 APFS 卷放工作区** | 推荐，一劳永逸 |
| 2 | **CI 里跑一次 Linux 构建 / 测试** | 最终门禁，无法规避 |
| 3 | 迁移前做冲突自查 | 已实测本工作区 **0 个**冲突 |

**在 Mac 上建大小写敏感卷**

```bash
diskutil list                                        # 先确认盘号
diskutil apfs addVolume disk1 APFSX mir2ws -caseSensitive
```

**冲突自查（在源机器上跑，输出为空即安全）**

```bash
find $WS -not -path '*/.git/*' -printf '%p\n' | tr 'A-Z' 'a-z' | sort | uniq -d
```

⚠️ **git 的陷阱**：大小写不敏感的文件系统上，**纯大小写改名会被 git 静默忽略**
（`core.ignorecase=true`）。必须两步：`git mv a tmp && git mv tmp A`。
D-03 的资产规范化也会踩到这条。

## D-21 禁 cgo（`CGO_ENABLED=0`）

**状态：已定。**

**依据**：`CGO_ENABLED=0` 一次买到三件事：

1. **Mac 上开发、一条命令交叉编译出 Linux 部署产物**——
   `GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build`。有 cgo 就没这么轻松。
2. **静态二进制**：无 glibc 版本耦合，容器基础镜像可以做到极小。
3. **构建可复现**：不依赖宿主机的 C 工具链版本。

**现状**：`mir2go` **已符合**，继承即可——它的
`internal/storage/sqlite/store.go` 开头就写明这个理由，SQLite 用的是
`modernc.org/sqlite`（纯 Go）而不是 `mattn/go-sqlite3`（cgo）。

**规则**：新增依赖**优先选纯 Go 实现**；确实需要 C 库时**先讨论**，
不要默默引入 cgo（它会同时破坏上面三件事）。

## D-22 地图源目录（**已定**）

`$WS/mir2go/data/map` 是参照服务端自行收集的一套，来源与版本都不如客户端集可考。

**事实**：原始地图有**两份**，内容并不一致（实测见 [assets.md §3.3c](./assets.md)）。

| 来源 | 张数 | 体积 | 用途 |
|---|---:|---:|---|
| `$WS/mir2c/map` | **770** `.map` + 1 `.mex` | 253.7 MB | **客户端**自带（assets.md §2 记的就是它） |
| `$WS/mir2go/data/map` | 605 | 242 MB | **参照服务端**自带 |

规范化名字后可配 **557** 对：**552 对逐字节相同，5 对内容不同**：

2. **`mir2go` 的地图不参与**。对拍遇到那 5 张差异（[assets.md §3.3c](./assets.md)）时，

4. **解析器要尽早支持 36 B/格**：客户端集里 **39 张**是这种布局（26.7 MB），
   其中 **`4.map`（8.6 MB）** 是体量最大的核心图之一；不支持的话 M1 一进主城就撞上。

## D-23 真实客户端 IP 如何从 gate 传到后端

**状态：已定（2026-10-07）—— 采用 ① PROXY protocol v1。**

**背景**：这是 [D-17](#d-17-gate-不做协议感知) 的直接后果。旧协议"往登录首帧的文本 token
末尾拼 `|<IP>`"这一手没法照搬 —— 新协议里不再有那种"可以顺手拼一段"的定长串字段
（自研协议的好处之一，见 protocol.md §10），而且那种做法本身就是**客户端自报**。

**为什么需要它**：后端目前不用 IP 做判定，但一旦要做**封禁 / 同 IP 多开限制 /
登录审计 / 反外挂画像**，就必须有一个**不可伪造**的来源。

**决策**：gate 在**连上后端之后、转发任何游戏数据之前**，先写一行 ASCII：

	PROXY TCP4 <源IP> <目的IP> <源端口> <目的端口>\r\n
	PROXY UNKNOWN\r\n                                  ← 拿不到地址时（规格允许）

后端剥掉这一行，之后的字节流**原样不动**。

**为什么是它**

| 方案 | 结论 |
|---|---|
| **① PROXY protocol v1** | **采用**。它是为这件事发明的标准（nginx / Envoy / AWS NLB 通用），且天然满足 D-17：gate 只是写下自己**本来就知道**的东西，完全不必理解游戏协议；后端也不必在 schema 里多一个"只有网关该填"的字段 |
| ② 后端向网关发起内部查询 | 否。多一条内部控制通道，且 gate 从"无状态"变成"有状态"（要维护连接元数据的生命周期） |
| ③ 把 `client_ip` 放进 `ClientHello` | 否。**等于相信客户端自报**（谁都能自称 1.2.3.4），且污染 schema 语义 |

**两条硬规则**（缺一条，这道门就形同虚设）

1. **接入策略只有两种，没有第三种**：要么"必须带头"（缺头即断开），要么"完全不认"。
   「有头就解析、没头退回 socket 地址」是**可伪造**的 —— 能直连到后端的人自己写一行
   `PROXY TCP4 1.2.3.4 …` 就能冒充任意 IP。实现里刻意没有这个中间态（`internal/proxyproto`）。
2. **后端只监听内网/本机**（如 `127.0.0.1:7200`）。第一道门是"外部根本连不到后端"，
   头校验是第二道 —— 别把全部希望押在头校验上。

**落地**

| 位置 | 做什么 |
|---|---|
| `server/internal/proxyproto` | v1 的读写两端（`WriteV1` / `ServerConn`）：严格校验、限长 107 字节、等头有超时（读完即清，不留给协议读）、认出 v2 魔数并明确报错；头之后的字节经缓冲包装后**一字节不少** |
| `server/cmd/gate` | 每条上游连接先写头（`-proxy-protocol`，**默认开**）。对端不认识该头时关掉（例：把网关挡在参照系统 `mir2go` 前面做对拍） |
| `server/cmd/gamesvr`、`server/cmd/accountsvc` | `-proxy-protocol`（**默认关** = 直连调试）：打开后**要求**头，缺头即断开；真实地址用于 AdminList 匹配与全部日志 |

⚠️ **默认值刻意不对称**：gate 默认开（一个不说明"背后是谁"的网关没有意义），
后端默认关（默认拓扑就是直连 —— `mir2cli` 与客户端回归都直接连 `:7200`）。
把 gate 摆到前面时，后端的这一项**必须**跟着打开，否则所有连接看起来都来自网关自己
（启动日志会明确打印当前来源，见两处的 `客户端地址来源:` 一行）。

**顺带删掉的东西**：`wire.LoginToken` 的 `ClientIP` 字段与 `<idx>|<IP>` 解析已删除 ——
它既是"客户端自报"，又与 PROXY 头构成**两个真相来源**（而且客户端可以覆盖网关给的值）。

**反悔条件**：若将来需要 **UDP** 或 gate 与后端**跨进程**共享连接元数据，
那是走 v2 二进制头（`internal/proxyproto` 已能认出并给出明确报错），而不是换方案。

## D-24 口令怎么过网络

**状态：已定（2026-10-08）—— 采用 ① 挑战应答。**

**状态：待决（2026-10-07）。** 它挡着新协议的 `Login`：新协议入口 v0 目前只能
用 `Reconnect` 认领**既有**会话（会话由 accountsvc 的真实口令校验产生），
见 [protocol.md §11](./protocol.md)。

**问题**：`account.proto` 里 `Login.password_hash` 注释写着"客户端只发哈希，明文不落网络"，
但存储侧是 **PBKDF2-SHA256 + 服务端随机盐**（`storage/password.go`）——
客户端**拿不到盐**，所以它算不出服务端能校验的那个哈希。三者只能选一：

| 方案 | 说明 | 代价 |
|---|---|---|
| ① **挑战应答**：`ServerHello.session_key` 下发 nonce，客户端发 `HMAC(客户端口令派生值, nonce)` | 明文与等价口令都不落网络；`session_key` 已经在握手里留好了位置 | 需要一次"取盐"往返（或把盐随账号一起下发）；两侧都要实现 |
| ② 客户端发**预哈希** `SHA256(pw)`，服务端存 `PBKDF2(SHA256(pw), salt)` | 实现最简单，`VerifyPassword` 原样可用 | **改存档格式**（现库里的哈希是对明文算的）⇒ 需要迁移或重建账号 |
| ③ 网络层加密（TLS / 自研握手）后直接发明文 | 最直白 | 引入 TLS 依赖或自研加密，与 C-7（零运行期依赖）要一起权衡 |

**为什么不能"先随便选一个"**：它是**认证**，改起来要动两端 + 全部存量账号。
**决策：两步往返，服务端始终不知道口令。**

```text
客户端                                          服务端
  │ LoginSaltRequest{account}                    │
  │ ──────────────────────────────────────────►   │  查账号（不存在也回一个随机盐）
  │ LoginSalt{salt, iterations, key_len}          │
  │ ◄──────────────────────────────────────────   │
  │                                               │
  K    = PBKDF2-SHA256(口令, salt, iterations, key_len)
  proof = HMAC-SHA256(K, nonce ‖ account)         ← nonce = 握手时的 ServerHello.session_key
  │ Login{account, password_hash: hex(proof)}      │
  │ ──────────────────────────────────────────►   │  用**存着的 K** 重算一遍 HMAC 比对
  │ LoginResult{code, session_token}               │  （`authn.CheckProof`，常量时间）
```

三样东西都不落网络：明文口令、`K`（等价口令）、连 `proof` 本身也绑在**这条连接一次性**的
nonce 上（嗅到也重放不了）。服务端能这么验，是因为它**存的就是 `K`** —— 存着的派生值
可以直接当 HMAC 密钥用，这正是它能做到"不知道口令也能验口令"的原因。

**为什么否掉另外两条**

| 方案 | 否掉的理由 |
|---|---|
| ② 客户端发 `SHA256(pw)` | 要**迁移存量账号**（现库里的哈希是对明文算的），而且发上去的 `SHA256(pw)` 本身就是一个**可重放的等价口令** —— 与①相比白白多付一个迁移成本 |
| ③ 明文 / 网络层加密 | 明文只在内网可接受（原版就是这样）；TLS 要引依赖（与 C-7 权衡），而我们并不需要加密整条信道，只需要"口令不落、且不可重放" |

**三条硬规则**（缺一条这道门就漏水）

1. **不区分"账号不存在"与"口令错"**：`LoginSalt` 对不存在的账号也回一个**随机盐**，
   `Login` 一律回 `LOGIN_BAD_CREDENTIALS`。错误码上泄露"这个账号存不存在"是白送情报
   （legacy 路径原本就是这么做的，见 `authn` 包的文件头）。
2. **KDF 参数由服务端下发**（盐/迭代/派生长），客户端**不许写死** —— 否则服务端哪天调
   迭代次数，所有客户端会一起登不上去（而且现象是"口令明明对却上不去"）。
3. **nonce 必须每条连接一份、且服务端要留下来** —— 它是"证明不可重放"的全部依据。
   丢了它，这套就退化成"发等价口令"（与方案②同级）。

**落地**

| 位置 | 做什么 |
|---|---|
| `protocol/account.proto`、`envelope.proto` | `LoginSaltRequest` / `LoginSalt`（0x0205/0x0206）；协议版本 3 → 4 |
| `server/internal/authn` | **登录校验唯一一份**：`ExpectedProof`/`CheckProof`（HMAC-SHA256 + 常量时间比较）与锁定策略 `LockPolicy`（`accountsvc` 的 legacy 路径也改用它 —— 安全策略同样只允许有一份，R-7） |
| `server/internal/storage` | `KDFParams()` 暴露盐/迭代/派生长（与 `HashPassword` 同一组常量）；`SessionStore.Create` 落一条已认证会话 |
| `server/internal/gamesvr` | 两步处理器；成功后签发**会话号即 token**（与 `Reconnect` 同一条尾巴）；失败按 `authn` 的策略记数/锁定 |
| `client/core/src/auth.rs` | HMAC-SHA256 + PBKDF2-HMAC-SHA256 自己实现（C-7），用 **RFC 4231** 与公开 PBKDF2 向量钉死，并与服务端**对同一组输入给同一组字节**（`proof_vector_matches_server`） |
| `client/core/src/entrance.rs` | 先取盐 → 算证明 → 发 `Login` → 成功后接选角那条尾巴（口令算完立刻从内存丢掉） |

**反悔条件**：要抗"服务端被拖库 + 弱口令"（离线爆破）就得换 PAKE（SCRAM/SRP）或加 TLS。
那时 `LoginSalt` 那一跳正好是 SCRAM 的 `server-first` —— 加一个服务端 nonce 往返即可，
**存储不用动**（存着的还是同一个 `K`）。

## D-25 屏幕文字用**真字体**（不再是纯 8×8 调试字体）

**背景（已实测）**：客户端原来所有文字都走 SDL3 内置的 8×8 调试字体，**只认 ASCII**
（`client/app/src/main.rs` 文件头写明）。于是**中文一律画不出来** ——
角色名（`勇士`）、职业（`战士`）、怪物名、聊天、弹窗提示……统统是空白或乱码。
而这不是"调试期的将就"：这套素材的内容全是中文，选角界面要显示的第一样东西就是名字。

**原版是怎么画的**：GDI + **系统字体**（宋体）：

```text
BoldTextOut(surface, x, y, clWhite, clBlack, UserChr.Name);   // IntroScn.pas:1519
```

`BoldTextOut` 内部就是 `CreateFontIndirect` + `TextOut`（`ClFunc.pas:605`）——
即"用一份字体文件画字"**本来就是原版的做法**，不是我们取巧。

| 方案 | 取舍 |
|---|---|
| ① **纯 Rust 光栅器 + 外部字体文件**（采纳） | `fontdue`（无 C 依赖、支持 `.ttc` 集合）+ 按序找字体：`$MIR2_FONT` → 资产目录 `font.ttf/otf/ttc` → 系统字体（macOS 优先**宋体** `Songti.ttc`，Windows `simsun.ttc`，Linux Noto/文泉驿）。与其它素材同一条纪律：**字体不进仓库** |
| ② SDL3_ttf | 要再构一个 SDL 子库（连带 FreeType/HarfBuzz），与 D-04 的"静态自构建"叠加成两份构建负担；我们只需要"把字画出来"，不需要排版引擎 |
| ③ 位图字库（HZK16 之类） | 观感与宋体差得远（点阵 vs 矢量），而且要往仓库塞一份来源不清的二进制 blob |
| ④ 继续只用 8×8 | 中文永远画不出来 —— 这条已经不是"将就"而是"做不了" |

**两条纪律**（都在代码里注释了）

1. **载入即自检**：候选字体必须**真的画得出汉字**才算数（`text::Face::probe`：
   私用区之外的常用汉字 + 位图非空）。`.ttc` 里第 0 个 face 常常是拉丁字体，
   光"文件能打开"会让界面变成一片空白 —— 那是最难查的症状。
2. **找不到就降级**：一份都用不了 ⇒ 退回 8×8 调试字体（画不出中文，但界面不崩、
   也不空白），并在终端说清楚，附上 `MIR2_FONT=/path/to/宋体.ttc` 的解法。

**落地**

| 位置 | 做什么 |
|---|---|
| `client/core/src/text.rs` | 找字体（含自检）+ 光栅化 + 量宽/行度量。**纯计算，没有 SDL** |
| `client/app/src/font.rs` | 字形 → 纹理缓存（**白色字形 + `set_color_mod` 着色**）+ 描边（错开 1px 画黑，照原版）+ 降级 |
| `client/app/src/ui.rs` | 界面图加 `draw_tint`（选角界面靠它压暗未选中的小人） |

**代价（写清楚）**：字形纹理按 `(字, 字号)` 缓存，界面字号固定 `UI_PX = 14`
（原版是 GDI 宋体 12pt，点→像素依赖 DPI，**没有逐像素对拍**）。

**反悔条件**：要支持"任意字号/富文本/换行排版"就该换成 `swash`/`cosmic-text` 这类
真正的排版栈 —— 那时 `core::text` 的接口（`glyph`/`width`/`metrics`）就是它的最小子集。

## D-26 选角界面：**照原版两个固定槽**，不是可滚动列表

**背景**：登录成功后原来是"状态机自己选列表第一个角色"，一路进游戏。
现在要有真的选角界面（原版 `IntroScn.pas` 的 `TSelectChrScene`）。

**照抄的关键几条**（都逐字核过原版）

1. **两个固定槽**，不是列表：槽 1 = 槽 0 整体 `+340,+2`（`IntroScn.pas:1431-1438`）。
   槽位坐标还**按 (职业, 性别) 各有一套**（`IntroScn.pas:1390-1429`，女性职业的石化/站立位置不同）。
2. **小人来自 `ChrSel.wil`**（按 Job/Sex 预渲染的序列，站立基址 `40+Job*40+Sex*120`），
   **不是** `Hum.wzl` 那套 actor 公式 —— 所以选角界面**不需要** `dress`，
   只要 `(job, sex)`。这也是为什么**服务端必须下发性别**（见 protocol.md §11）。
3. **没有箭头、没有高亮框**：选中 = 播站立动画（16 帧/300ms），未选中 = **石化**定格
   （13 帧）。另有 `MakeDark` 那层压暗，但它是**过渡**效果（`SelectChr` 把 `DarkLevel`
   置 30，而 `MakeDark(dd, 0)` 直接 `exit`，`CliUtil.pas:749`）⇒ 我们只实现站立/石化。
4. **按钮平时不画**：背景图 `Prguse[65]` 里**已经画好**按钮外观，`Prguse[66..72]`
   是**按下态**叠加图（原版只在 `Downed` 时画，`FState.pas:2693-2705`）。

**我们有意加的两处（都不改鼠标行为）**

| 加的 | 为什么 |
|---|---|
| **键盘**：←→↑↓ 换槽、回车进入 | 原版选角**只认鼠标**（`TSelectChrScene` 没覆写 `KeyDown`）。开发时不用摸鼠标 |
| **[新建]/[删除] 弹一条诚实的说明 | 这两颗按钮**画在背景里**（没法"不显示"），而新协议下 `CreateCharacter`/`DeleteCharacter` **服务端还没实现** ⇒ 点了会说明现状与替代做法（`mir2cli -new-char`），而不是静默没反应（**现已接上，见 D-35**）|
| **默认选中第一个槽、其余一进来就是石化** | 原版 `OpenScene` **什么都没做** ⇒ 两个都站着、都不选中：**看不出当前选的是谁**，而且这时点[开始]会被服务端拒掉（两边 `Selected` 都还是 FALSE）。这条是"把原版一个坏状态改掉"，不是漏做 |
| **站立动画 150ms/帧（原版 300ms）** | 原版 16 帧 × 300ms = **4.8 秒一圈**。实测 16 帧**帧帧不同**（是一段真动画，不是静帧也不是方向帧），但用户反馈"看上去非常慢" ⇒ 取 150ms（2.4 秒一圈）。要还原改一行常量 `Art::STAND_MS` |

**"手动选角"怎么接**：`Entrance` 加 `set_manual_pick(true)` + `pick(id)` + 新阶段
`AwaitPick`。默认仍是"自动选第一个"（e2e / 无头驱动不想为选角多写一层）——
所以这是个**显式开关**，不是"有列表就停"（那样 e2e 也会停下来等）。
选角被拒（如租约被占）在手动模式下**退回选角**让人换一个，而不是判死。

**落地**：`core/src/select_ui.rs`（版式 + 图号 + 动画状态机，纯计算）/
`app/src/select.rs`（绘制 + 输入）/ `core/src/entrance.rs`（`AwaitPick`/`pick`）/
`server/internal/gamesvr/netproto.go`（`Gender`）。

**反悔条件**：原版是"两个槽"，因为它 1.76 就只允许两个角色；哪天要放宽到 N 个角色，
版式要改成列表（那时 `slot_at` 与 `Layout` 的 `slot_hot: [Rect; 2]` 是唯一的改动面）。

## D-27 选角版式**从素材量**，不照抄原版坐标

**背景（用户实测报的）**：选角界面里，功能按钮的可点击位置、按下态叠加、小人位置
**与背景贴图上画的位置对不上**。

**根因**：官方的坐标（`FState.pas:904-925`、`IntroScn.pas:1390-1538`）是写给
**官方 1.76 那套 `Data\Prguse.wil`** 的，而 **我方的素材不是那一套**：

| | 官方 1.76 | 我方素材（`mir2c/data`） |
|---|---|---|
| 两块面板的间距 | `340` | **`552`** |
| 中间菜单的行距 | `38` | **`19~20`**（按钮图高 21，本来就叠 1~2 像素） |
| 两块「选择」按钮 | 槽热区 `(134,424)`/`(602,424)`，96×74 | **`Prguse[66] @ (133,452)` / `Prguse[67] @ (685,453)`，76×33** |
| 中间菜单项 | 开始游戏/新建角色/删除角色/…/退出 | 开始/**创建人物**/**删除人物**/**制作群**/退出 |

⇒ 照抄官方坐标 = 点击区、按下态、小人、文字**一起偏**（正是用户看到的现象）。

**做法：量，然后钉住**

| 量什么 | 怎么量（**有界**计算） |
|---|---|
| 两块「选择」按钮 | 把按下态图当模板在背景上滑，差异最小处即按钮矩形 —— 实测左 4.45 / 右 4.37（次好 16+，判别度足够），**位置与图号一起确定** |
| 中间 5 项的行位置 | 面板内"亮像素行直方图"分组（y ≈ 465/497/517/536/557） |
| 菜单项的按下态图 | 尺寸与文字宽度一一对应（2/4/4/3/2 个字 ↔ 44/120/120/92/56 像素）⇒ 就是 `Prguse[68..72]`（**与官方是同号同语义**，只是位置不同） |
| 两块人物区（凹槽） | 行/列**暗度剖面**（大块暗区） |
| 名字/等级/职业 三行 | 面板内亮框的行位置（y ≈ 481/510/539，行距 29） |

这些数字写进 `core::select_ui`，并由测试 **`真素材_按钮与背景对齐`** 守住：
两块「选择」的按下态图在实测位置上与背景图**逐像素比、平均差 < 8** —— 改素材或改坐标
这条会红（这正是用户报的那个 bug 的判据）。

**小人怎么放**：不再维护原版那 6 组 `(职业, 性别)` 写死偏移，改成**一条规则** ——
把小人图**不透明包围盒**的底边中点对齐到凹槽的底边中点（`place_sprite` + `alpha_bbox`）。
理由是人物图四周的透明边各图不同，按整图对齐会让不同职业/性别的小人**高低不一**；
按内容对齐则自动适应，且不用维护表。

**⚠️ 一条工程教训（写在这里，别再犯）**

量版式时我连着两次写出**嵌套暴力搜索**（`位置数 × 模板像素` ≈ 10~26 亿次），
把开发机单核跑满几分钟，被用户抓了两次。规矩定下来：

> 测量/扫描类工具必须在代码里**写明算力预算**（量级算式），
> 只用"采样点粗筛 + 候选复核"或"降采样粗筛 + 全分辨率复核"，
> 单次上限控制在**千万级**（毫秒~百毫秒）。

**反悔条件**：哪天素材换成官方那一套，本表的数字要重测（测试会红，正好提醒）。

## D-28 音频：**自己写的软件混音**（走 SDL3 的音频流），不引第三方音频库

**背景**：客户端要接上音乐与音效。原版是两套后端：音效走 DirectSound（**每个音效
`new` 一个 buffer 叠着播**，`DXSounds.pas:1852-1881`），音乐/MP3 走 DirectShow（`Mpeg.pas`）。

**选项**：

| 做法 | 好处 | 坏处 |
|---|---|---|
| `rodio` / `kira` / `cpal` | 现成 | 新依赖（本机缓存里也没有）；而 `sdl3` 本来就给了设备 |
| `sdl3` 的 `mixer` feature（SDL_mixer） | 现成混音 | 多一个 C 库（`sdl3-mixer-src` 3.2.4），与"运行期零依赖"（C-7）相性差 |
| **`sdl3` 音频流 + 自写混音** | 无新依赖；混音每一块都能单测 | 自己写那一百多行（格式转换 / 重采样 / 叠加 / 削顶） |

**已定：自写。** 理由：D-01 的依赖清单里 `sdl3` 本身就含音频；混音的每一块
（采样格式、单声道→立体声、重采样、多路叠加、两组开关）都能**不接声卡**单测
（`client/app/src/audio.rs` 的测试就是这么写的）；换成 SDL_mixer 会把这层变成黑盒。

**顺带修正 D-01 的一条**：那条写的是"`minimp3-rs` + 自写 WAV 解析"。现在：

* **WAV 用 SDL3 自带的** `AudioSpecWAV::load_wav`（`sdl3-0.20`）—— 它已经在依赖里了，
  再自己写一个 RIFF 解析没有收益；
* **`minimp3` 暂时不引**：进图音乐 `Music/<号>.mp3` 现在**没有资产**（`mir2c/wav` 里
  一个 mp3 都没有）、协议里也还没有地图音乐号。等那条路真要用时再引，现在引是死代码。

**音量**：照原版**只有两个开关**（音效 / 音乐，`MShare.pas:213-214`），不做音量滑条、
不做距离衰减、不做 pan —— 那三样原版都没有（`SoundUtil.pas:180-192` 只查
`FileExists` 然后放）。同理**不做毫秒级节流**：原版的去重是**动作级**的
（`m_boRunSound`，`Actor.pas:2357-2359`，一招只响一次）。我们只在软件混音这一层加了
"同一条音效 30ms 内不重复"与"最多 24 路"，理由是触发点从"动作开始"变成了"每帧看世界
状态"，**这是接线方式的差异，不是规格**。

## D-29 音频产物：**转换**而不是打包压缩（无损压缩对这一堆是白费）

> ⚠️ **本条的产物形状已被 D-30 取代**：现在是**一个容器文件**
> （`assets/audio/sounds.m2pk`，kind=2 / codec=1），**BGM 16bit PCM 无损 + 音效 4bit ADPCM**，
> 41.6 MB（默认口径，2026-10-08 起）。
> 本条仍然有效的是**测量结论**（无损压缩对音频无效）与"音效 22.05k 单声道"的取舍依据。

**背景**：音频资产 209.0 MB（777 个 `.wav`），用户问"是不是原始未压缩 wav，体积有点大"。
量过之后：**全是未压缩 PCM**（775×16bit + 2×8bit；44.1k×771；257 立体声 / 520 单声道），
而且**七个长 BGM 就占 72 MB**（`Field2.wav` 一个 33.8 MB / 191.5 s）。

**先排除掉的那条路（实测，别再试）**：打包 + 无损压缩。

| 样本 | zlib | xz |
|---|---|---|
| `103.wav`（0.03 MB） | 52.7% | 44.0% |
| `144.wav`（0.07 MB） | 87.3% | 82.8% |
| `M55-2.wav`（0.81 MB） | 87.9% | 81.3% |
| `log-in-long2.wav` 前 8 MB | 96.1% | 93.0% |

音效是宽带噪声，压不动 ⇒ **不做容器、不做压缩**（省得白干一轮）。

**已定：转换**（`tools/wavpack/build.sh`，209.0 MB → **73.5 MB**，2.8×，1.5 秒）：

- 音效 → **22.05 kHz 单声道**。理由：原版**没有 pan、没有距离衰减**
  （`SoundUtil.pas:180-192` 查完 `FileExists` 就按原样播）⇒ 立体声→单声道**不丢游戏信息**；
  22.05 kHz 是那个年代的音效标准（这批素材里本来就有 4 个 22.05k 的）。
- **BGM 三首（登录 / 选角 / 自己死亡）保持原样**：音乐降采样听得出来。
- **原版从不播的长文件不产出**（省 40.1 MB）：`Field2.wav`（`bmg_field` 定义了但全代码未用）、
  `main_theme.wav`（播它的定时器被注释掉，`PlayScn.pas:485-486`）。
  ⚠️ 但**清单 `sound.lst` 引用了的绝不跳**——`Game-over2.wav` 正是这种
  （原版代码不播它，可清单第 49 号指向它）。
- **不做 ADPCM、不做 mp3**：前者要自写编解码（收益是 73.5 → 约 24 MB，**留作后备**：
  真要继续瘦身就做它，因为 SDL 的 WAV 加载器不认 ADPCM，得配一个自写解码器）；
  后者**没有素材**——客户端集里一个 mp3 都没有（`.mp3/.ogg/.wma/.mid` 全 `find` 过），
  所以"进图音乐"这条路**没有素材可接**，不是"等补素材"。

**验证**（写进工具，每次 build 都跑）：

1. 每个文件读回核对：头（PCM/单声道/16bit/采样率）、帧数、峰值同量级（±40%/120%，
   下界放宽是因为下混本身会降峰；真正的灾难"整段静音"单独判）；
2. **清单里源能播的编号，产物一个都不能少**（实测 **741 → 741** ✓）。
   这条就是为了防"瘦身顺手把某个音效弄丢"。

**顺手修的跨平台坑**：清单写 `wav\game-over2.wav`（小写），真文件叫 `Game-over2.wav`
（大写）—— macOS 上碰巧能播、**Linux 上直接找不到**。产物按清单的拼写输出（7 个文件受影响）。

## D-30 音频产物的形状：**一个容器文件** + 4bit IMA ADPCM

**背景（用户提的两点）**：「将音频资产打包成一个文件，不要呈现一堆散乱文件」，
「一个文件也能避免文件名大小写问题」；以及更早问的「体积有点大」。

**已定（同日实施）**：产物 = `assets/audio/sounds.m2pk` **一个文件**，
M2PK 格式的**第二种用途**：

| kind | codec | 谁写 | 内容 |
|---|---|---|---|
| 1 地图 | 0 brotli | `tools/m2pk` | `.map`（压缩收益大，253.73 → 8.83 MB）|
| **2 音频** | **1 原样** | `tools/wavpack` | 音效 + BGM + 编号表（209.0 → **41.6 MB**，音乐无损）|

三条理由，逐条对应实测：

1. **一个文件**：好分发、好校验；**而且大小写问题从根上没了** —— 容器里的键是
   规范化过的（小写、去扩展名、`[a-z0-9_~-]` 之外换成 `_`）：`Game-over2.wav`
   与 `game-over2.wav` **就是同一个键**。这个坑是真的：客户端集里清单写小写、
   真文件写大写，macOS 上碰巧能播、**Linux 上直接找不到**（转换器实测 7 个文件受影响）。
2. **codec = 原样存储（不压缩）**：实测 PCM 用 zlib 只能到 87~96%、xz 82~93%；
   4bit ADPCM 更压不动。压缩纯属浪费 CPU（压缩后 17.89 MB / 压缩前 17.89 MB，
   比率 1.0000）⇒ 干脆 `codec=1`，读侧直接切片，连解压器都不用进。
3. **4bit IMA ADPCM（`fmt=0x11`）**：体积 1/4；**波形域**编码 ⇒ 没有 MP3 那种
   变换域预回声（短促打击声最怕这个）；**样本精确** ⇒ 我们按动画帧对齐播的
   脚步/挥刀不会"慢半拍"（MP3 一帧 1152 样本 ≈ 52 ms，还得处理编码器延迟与填充）；
   编解码共一百多行，**零新依赖**（也就省掉 minimp3 那条依赖与它的 C）。

**质量代价：有数字，不靠感觉**。**音效**解码回来与原 PCM 的 SNR —— 最小 6.8 dB /
**中位 17.5 dB** / 均值 17.9 dB（BGM 是 16bit PCM，无损，不参与统计）。最差的是
**噪声型**素材（`470-1.wav` 零交叉 18012 次/秒，Nyquist 才 22050）—— 4bit 差分编码
对这类内容天生不友好。三档（**默认第一档**，2026-10-08 用户口径改的）：
`tools/wavpack/build.sh`（音乐无损 ⇒ **41.6 MB**）、
`MIR2_AUDIO_BGM_PCM=0`（音乐也有损 ⇒ 19.45 MB）、
`MIR2_AUDIO_CODEC=pcm`（全无损 ⇒ 79.8 MB）。原件 `mir2c/wav` 从不改动。

**试过并否掉的**：编码端一阶误差反馈（噪声整形，解码端不用改）—— 会把重建值顶到
±32767（源峰值 23363 → 产出 32767；减半阻尼后 22680 → 31718），削顶 artifact 比
那几 dB 的 SNR 更糟。**试过并排除的还有 MP3**（用户问过）：体积确实更小
（音效 64k + BGM 128k ≈ 11.7 MB），但换来预回声 + 对齐修剪 + 一个新解码器依赖，
而它的优势几乎全在 BGM 那 22 MB 上 —— 性价比不如 ADPCM。

**验证（三道，都是自动跑的）**：

1. 写侧自检①：解码回来与原 PCM 比 SNR（并列出最差的五个文件）；
2. 写侧自检②：**从容器里读回来**，清单里源能播的编号**一个都不能少**（741 → 741）；
3. 客户端跨语言：Rust 解 Go 写的容器 + Go 编的 ADPCM，并断言帧数等于 Go 写的 `fact`
   （实测 2932 帧 ✓）；另外用 `afconvert`（macOS 自带的 MS-IMA 解码器）解我们的产物，
   与本项目解码器**逐样本一致**（2932/2932，最大差 0）。

## D-31 美术产物的形状：**一个容器文件 + 每 32 张一组拼接**（实测 −430 MB）

> ⚠️ **取代 D-11 里"美术 `.wzl` 直读"那一行**（D-11 的地图/音频部分不变）。

**背景（用户提的两点）**：「美术资产也打包起来」；调研压缩时明确「**我们不需要通用压缩**」
「JPEG XL 也调研下」，最后定：「选 **分组拼接 + brotli**」。

**已定（同日实施）**：产物 = `assets/image/images.m2pk`，M2PK 的**第三种用途**：

| kind | codec | 谁写 | 内容 | 体积 |
|---|---|---|---|---|
| **3 美术** | **1 原样** | [`tools/artpack`](../tools/artpack) | 236 个图库（`.wzl`+`.wzx`，2,873,878 张图）| 1776.2 → **1346.0 MB（−24.2%）** |

**为什么不是"再压一遍"**：`.wzl` 已是每图一个 zlib 流，重压是 **101.2%**（实测）。
真正被浪费的是 **deflate 的 32 KB 窗口跨不了图** —— 图库里"同一动作的连续帧"高度相似，
上下文全丢。所以做法是**解出 raw 像素再按组拼**：一组的 brotli 流里有 32 张图可互参。
这也解释了 D-11 当年那句"全量 M2PK（每项独立压缩）体积 ≈ 现状"：按**项**独立压确实如此，
按**组**才有效。

**为什么 codec = 原样**：块内已经是我们的分组 brotli 流，容器再套一层毫无意义。
读侧因此可以**按范围读**（`Archive::read_range` + `Archive::open_lazy`）：只把索引读进内存、
每组按需 `seek` —— 1.4 GB 的容器不会顶爆内存（原来的 `Archive` 是整文件读，只适合 9 MB 的地图）。

**组大小（实测拐点）**：type 3 子集（hum/prguse/weapon）8/16/32/64 张一组 =
88.1% / 85.7% / **84.2%** / 83.1%；type 5 的 `objects25` 8 张 = 69.5%、32 张 = **65.3%**。
组越大越省，但一组是**随机访问单位**（取一张 = 解一组）⇒ 默认 **32**，且 `groupSize`
存在**每库**载荷头里 ⇒ 将来按库调粒度不用改格式。

**试过并否掉的（都有数字，2026-10-08）**：

| 手段 | type 5 | type 3 | 结论 |
|---|---:|---:|---|
| **WebP Lossless**（`cwebp -z 9 -exact`）| 77.7% | **116.9%** | ✗ 小精灵反而膨胀 |
| **JPEG XL**（`cjxl -d 0 -e 7`，libjxl 0.12）| 79.3% | **119%** | ✗ 同上，且要引更重的解码器 |
| PNG 逐行滤波 + deflate | 114~127% | 124% | ✗ 索引值不是空间平滑量 |
| 本地调色板 + k 位打包 | 106~111% | 142% | ✗ 破坏字节对齐 |
| 裁透明包围盒 | — | 100.6% | ✗ 透明区对 deflate 本就是"免费"的 |
| 高位/低位拆平面 | 95.6% | — | 只一点点，不值 |
| 帧间 XOR | — | 99.7% | ✗ 帧间没那么像 |
| **分组拼接 + brotli** | **76.5%** | **83.8%** | ✓ 采用 |

WebP/JXL 在 type 3 上翻车的原因量得很清楚：喂进去要**展开成 RGBA**（4 字节/像素）+ 每个
文件 **26~38 字节**固定开销，而我们的精灵中位只有几百字节、63% 是透明像素；喂"索引调色板
PNG"与喂 RGBA **结果完全一样**（libjxl 内部归一化）。两者都**逐像素校验过确实无损**
（RGB 与 alpha 两条通道分别对拍）—— 它们只是不适配这种小图，不是实现问题。

**纪律（与 kind 1/2 的差别）**：

1. **校验方式不同**：块内容重排过 ⇒ 不能"逐字节比源文件"。`artpack verify` 逐图比
   **记录 + raw 像素**（236 库 2,873,878 张，实测 **41.8 s 通过、0 源异常**）；
   `m2pk.Verify` 对 kind=3 **明确拒绝**，避免误用。
2. **像素解码只有一份**：`core/src/wzl.rs::to_rgba` 两条载体共用；客户端对拍
   **54,306 张逐字节一致**（`真素材_容器与直读逐字节一致`）。
3. **空库跳过**：源里有 16 个 `.wzx` 图数为 0 的库（`mon0`/`newui`/`objects11`/…），打包器
   跳过并打印原因；客户端遇到"容器里没有"回退裸目录 —— 两边行为一致（都是空）。
4. **确定性**：组各自独立编码 ⇒ 并行度不影响输出字节（有单测守着）。

**顺手修的**：`EncodeImageLib` 第一版把并行度**写死 8**，而本机 14 核 ⇒ 打包只跑到 761% CPU、
慢 ~40%（全量 15 分 10 秒）；改成 `GOMAXPROCS` 是后续构建的收益。

**落地**：[`tools/artpack`](../tools/artpack)（`pack`/`verify`/`info` + `build.sh`）、
[`internal/m2pk/image.go`](../internal/m2pk/image.go)（载荷编解码）、客户端
[`core/src/image_lib.rs`](../client/core/src/image_lib.rs) + [`core/src/m2pk.rs`](../client/core/src/m2pk.rs)
（懒加载 + 范围读）。用法与格式见 [assets.md §5c](./assets.md)。

**还没做的（不是遗漏，是取舍）**：e2e 的渲染回归仍走裸目录（`Wzl::open`），没有让渲染层
也吃容器；进图音乐（`Music/<n>.mp3`）那条与本条无关。

## D-32 建号：`CreateAccount` + 开关**默认关** + 每 IP 5 秒

**背景（用户问的）**：「建账号功能有了吗？不是建角」（2026-10-08，问了两次）；
口径确认：对话框**只收 账号/口令/确认**、开关**默认关** + 每 IP 5 秒。

**已定（同日实施）**：新协议加 `CreateAccount` / `CreateAccountResult`（0x0207/0x0208，
协议版本 **4 → 5**），流程复用 D-24① 的第一步：

```
① LoginSaltRequest{account} → LoginSalt{salt, iterations, key_len}
② K = PBKDF2-SHA256(口令, salt, iterations, key_len)
③ CreateAccount{account, verifier: hex(K)}    ← 建号必须把 K 送过去（见下）
```

**一句不粉饰的话**：D-24 说的"等价物不落网络"只对**登录**成立。建号时服务端手里什么都
没有，它必须拿到一个"以后能验登录"的值才存得下 ⇒ **那一刻的 `K` 就是口令的等价物**，
机密性只在本连接上成立（明文仍不落网络）。要更严只有上 TLS 或用 PAKE（OPAQUE 那类），
不在本次范围。协议注释里写明了这条差别。

**盐由服务端给、并留在会话上**：客户端不许自带盐（否则盐就不再是"服务端随机"）。
`onLoginSaltRequest` 把 `(account, salt)` 记进 `protoSession`，建号时要求 `saltFor` 对得上 ——
对不上就拒。这条不是洁癖：**实测第一次就踩到了** —— 客户端拿 `NewBie` 取盐、
入库却规范化成 `newbie`，`saltFor` 不匹配 ⇒ 若不拒就会存下一个"永远登不上"的号。

**三条纪律照原版**（`LoginSrv/LMain.pas:977-986`）：

| | 原版 | 本实现 |
|---|---|---|
| 开关 | `Config.boEnableMakingID`（**默认 True**，`LSShare.pas:96`）| `-allow-new-account`（**默认 False**）—— 开着等于把注册入口挂公网 |
| 节流 | 每**连接** 5 秒 | 每 **IP** 5 秒（`Server.createLast`，粗锁；>4096 项顺手清过期）|
| 重名 | `AccountDB.Index >= 0` | `storage.ErrExists`（并发下靠存储主键兜底）|

**与原版的差别（有意）**：

1. **只收 3 个字段**：原版收两个定长结构（`TUserEntry` + `TUserEntryAdd`：账号/口令/姓名/
   身份证/密保 1/密保 2/生日/手机/邮箱…，`Grobal2.pas:587-604`）全落库；我们只收
   `account + verifier` —— 存储没有那些列。
2. **口令长度只有客户端把关**：服务端只收到校验值，从来见不到口令 ⇒ 由
   `app::login::try_signup` 查"至少 3 位 + 两次一致"（原版客户端 `CheckUserEntrys` 同款；
   原版服务端也不查口令）。
3. **建完不自动登录**：与原版一致（`ClMain.pas:3684-3691` 只是弹个提示）—— 状态机停在
   `Stage::SignedUp`，界面提示后把人送回登录框。
4. **账号名统一小写入库**（3..14 位、`[a-z0-9_]`，`authn.NormalizeAccount`），
   **查库一律先规范化**（`authn.CanonicalAccount`）—— 但 D-24 证明里的 `account` 用
   客户端**原样**字符串（两端要对齐），为什么不能合成一个变量写在该函数注释里。

**界面**：复用登录对话框（原版 `DNewAccount` 是另一张面板图，本套素材没有 ⇒ 标题与字段名
用调试字体画，与"中文打不进来"同一条已知限制）；`[确定]/[取消]` 用原版建号面板那两颗素材
（`Prguse[51]/[52]`，摆在原版 `[新用户]/[修改密码]` 的槽位上）。⚠️ 原版的 `[X]`（图号 83）
在本套素材里**是空壳**（0×0）⇒ 关面板用登录框自己那颗 `[X]`。

**验收（都是自动跑的）**：

   重名 ⇒ 拒；5 秒内第二条 ⇒ 拒；5 个非法名 ⇒ 拒；**建完立刻用它的口令登录成功**

**落地**：协议（`account.proto` + `envelope.proto` + `version.txt`（当时 5，现已随 D-34 冻结回 1）+ codegen，两端黄金报文同步更新）、

## D-36 两条"画面没跟着状态机走"的 bug —— 以及**为什么测试没拦住**（把决策搬出主循环）

**背景（用户，2026-10-08）**：① 建角之后选角窗口不立刻显示新角色（要重登）；
② 选角并开始后听得到受击/死亡声，但**画面没切到游戏**。修完之后用户追问：
**"这么显著的问题，你的测试用例是怎么通过的？"** —— 这条把答案与对策都记下来。

**根因（两条都在主循环里）**：
1. 重建选角场景那条分支的守卫写成 `mode != 4 && Stage::AwaitPick` —— 而**建/删角恰恰发生在
   已经在选角屏的时候**（`mode == 4`）⇒ 整条分支被跳过：服务端回了新列表、状态机也更新了，
   界面就是不重建 ✗（重登时 mode 变过，才命中）。
2. `mode = 2`（游戏主场景）全仓只有三处：启动带会话号、按 F2、门放完且**没有选角**那条路 ⇒
   **选角通过后没人切** ✗。旁证：`Select::start_clicked` 被 set 了两处、**没有任何地方读它**
   —— 它本该是这次切换的触发器，却从来没接上（已删）。

**为什么测试全绿**（三层，逐层都成立）：
- app 那 40 多条测试测的是**纯函数与小对象**（状态机、`select.rs` 的场景、`wrap_px`…），
  而这两条判定**写死在主循环里** —— 主循环要 SDL 窗口与素材才能跑，测试结构上碰不到；
- 我上一轮确实写了 `list_changed` 的测试 —— 但**它测的是 helper 本身（那是对的），
  没测它的调用点**（错的是外面那个守卫）⇒ 典型的"测了函数、没测接线"；
- `mir2-e2e world` 也拦不住：它按 D-18 **不含 SDL**，验的是"状态机对"（`in_world`、位置、
  实体），而这两个 bug 全在**画面分派**那一层 —— e2e 天生不覆盖。

**对策：把"每帧网络 → 画面"的决策搬进纯函数 `plan()`，主循环只当执行器**：
```rust
fn plan(mode, awaiting_pick, in_world, changed, door_blocking) -> Plan
//   rebuild_select = awaiting_pick && changed          ← bug① 曾经在这里多一个 mode != 4
//   enter_select   = awaiting_pick && !door_blocking
//   enter_play     = mode == 4 && in_world             ← bug② 曾经整个不存在
```
判据**全是状态机说的事实**（`Stage::AwaitPick` / `in_world()` / 列表有无变化 / 门放完没），
没有一处是"猜的时机"。

**这条测试是"真会红"的 —— 实际验过**（不是嘴上说）：
把 `rebuild_select` 改回 `… && mode != 4` ⇒ `换屏判定` 红在
"在选角屏里也必须按新列表重建"；把 `enter_play` 写成 `false` ⇒ 红在
"选角通过必须换到游戏主场景"；改回来即绿（文件逐字节还原，`cmp` 验过）。

**还剩下的洞（诚实记账）**：主循环**本身**仍没有自动化测试 —— `pump()`、绘制分派、
SDL 事件路由、`mode == 1`（门）那条分支、BGM 随模式切换等，都还只能靠人眼。
现在比以前好的只是"**换屏决策**这一块被搬出来了"。可行的下一步（有人再投时间时）：
按 D-33 已有的先例（`mir2-e2e login -door 1500 -out x.png` 能**合成一帧**）扩一个
"无头渲染冒烟"：合成"选角屏""进图那一帧"两张图做断言。

- 按住时每 ≥300ms 重触发一次，松手清目标（`ClMain.pas:2115-2116 / 2384-2389`）。

**落地（三处）**：
1. **协议**：`MoveInput` 加 `bool run = 5`（带默认值的可选字段 ⇒ 老客户端行为不变，
   **不需要** bump `version.txt`；顺手清掉了 protocol.md §11 那条"没有走/跑标志"的待办）。
2. **服务端**：`onMoveInput` 按 `run` 选节流（`MinRun`）与**步数 2**；
   `movePlayerSteps` **一格一格走、撞墙就停**（不是"算一个 +2 的落点"—— 中间有障碍时结果不同）；
   legacy 的 `CM_RUN` 也从"只是节流短一点"改成真的 2 格（那条以前也是错的）。
3. **客户端**：新增 `Cmd::Run(dir)`；游戏视图里**左键=走 / 右键=跑**（**离线看地图时左键仍是
   那个诊断探针** —— 开发用的，别和走路抢键）；松手清目标；按住时按
   `WALK_MS = 650` / `RUN_MS = 450`（比服务端 600/400 稍慢，免得每步都被拒）一步步朝目标格走，
   到了就停。

**验收**：服务端 `TestWalkOneCellRunTwoCells`（走 1 格、跑 2 格、撞墙即停）；
客户端 `鼠标方位给方向`（8 个方位 + 同一格 ⇒ `None` ⇒ 调用方据此判"到了"）、
`屏幕与格子互为逆`（"点哪走到哪"的换算）。全量：`cargo test --workspace` 44/121/7/3、
`go test ./...` 25 包全过；两端 clippy / gofmt 干净。

**照原版还差的地方（记账）**：① 相邻（≤2 格）时原版只转向不发移动 —— 我们直接发移动
（服务端会走一步或原地转向，观感差别很小）；② `Ctrl+左键=跑` 没接（右键已够用）。
