### 0.1 实测：`$WS/mir2.exe` 是登录器，**不含**美术（2026-10-07）

`$WS/mir2.exe`（129,739,520 字节，PE32）**不是游戏客户端**，而是**盛大登录器**。
7-Zip 对它自动识别失败（自定义 SFX stub），但**偏移 `40,876,032`（0x26FB000）处内嵌一个 7z 归档**：

```bash
tail -c +40876033 mir2.exe > payload.7z    # 从 7z 魔数(37 7A BC AF 27 1C)偏移切出
7zz x -o./sfx payload.7z
```

解出 21 个条目，**全部是启动器模块**：`Legend.exe`（29 MB 启动器）、`LaunchLegend*.update` ×11
（PE DLL 模块）、`MyMirLoader*.update`、`Legend_MirOld.update`、`Launch100m_b.dll`、
`v1.avi`（26 MB 开场视频）、`Legend.ini` / `LegendCfg.ini`。

- **无任何 `.wil` / `.wix`**；`Legend.exe` 的 PE 资源只有 Delphi VCL 自带位图（`BBABORT.bmp` 等）。
- `Legend.ini` 的 `[Download] Dir=` **为空**、`[WilImage]` 段为空 ⇒ 登录器尚未配置客户端下载源。

⇒ **不解决 D-15。** 需要的是**游戏客户端目录本体**（含 `Data/*.wil`、`Graphics/*.wil`、`Wav/`、`Music/`），
而不是登录器。素材来源仍需你裁决（自有副本 / 购买 / 其它来源）。

## D-01 技术栈

**状态：已定。**

| 端 | 选型 | 理由 |
|---|---|---|
| server | **Go** | 从 `mir2go`（63,867 行）抽取领域层，省掉最大的重复劳动 |
| client | **Rust + SDL3** | exe 3–5 MB、运行期零依赖、Win/mac 一套代码 |

客户端依赖清单（就这些，全部静态编进去）：

- `sdl3`——窗口 / 输入 / 音频 / 计时 / 线程
- `softbuffer` 或 SDL3 `gpu`——上屏（见 D-07）
- `prost` / `prost-build`——协议代码生成（见 D-12）
- `minimp3-rs` + 自写 WAV 解析——音频
- 字体：**自带点阵字库**（原版本身就是位图字库），零字体依赖

构建参数（体积）：`opt-level="z"`、`lto="fat"`、`codegen-units=1`、`panic="abort"`、
`strip=true`、Windows 加 `+crt-static`。

## D-02 全栈 UTF-8，弃 GBK

**状态：已定。**

**协议自由后，本条从"三个后果要处理"简化成"一条规矩"**：

> 协议层只搬字节；rune 安全的截断/换行只在 UI 层做。

原先因 Delphi `String[N]`（字节口径）而产生的三个后果——**字节容量预算、`EqualFold` 比较语义、
排序口径——全部作废**（不再有定长字节名字段）。

**转码只发生在边界**：

- `mir2go` 侧运行期唯一转码点 `internal/castle/sabuk.go:336 decodeGBK` 必须下沉到导入工具。
- 新 `mir2` 服务端**不允许**出现任何运行期字符集转码。
- 所有 loader 加 `utf8.Valid` 断言：非法即启动失败，不要静默乱码。

**遗留数据导入**：`mir2standard` 的配置、`mir2go` 的 `data/` 都是 GBK 或混合编码，
在**导入那一刻**转成 UTF-8，之后全链路 UTF-8。

## D-03 文件名全小写、无中文、`/` 分隔

**状态：已定。**

**依据**：一次性消灭三个跨平台坑（大小写敏感文件系统、GBK 文件名、反斜杠）。
macOS 默认大小写不敏感，会**掩盖**大小写 bug——由本条一次性消灭。

**新项目是"自己的资产树"，可以完全自己定义**（不再被原版文件名绑架）：

- 资产树由 `tools/` 从 `mir2standard` / `Mir2-GeeM2` **生成**，命名规则自己定。
- 若沿用原版文件名（`Data/Hum.wil` 等），需做规范化：`data/` 侧实测 **855 个大写名 +
  324 个非 ASCII 名**（分布见 [legacy-analysis.md §7](./legacy-analysis.md)）。
- `data/monitems/*.txt`（300 个中文名）**文件名即怪物名**——不要重命名，
  改为索引文件，摆脱"文件名当数据主键"的耦合。

**做法**：一次性 `tools/assetnorm`，产出并提交 `normalize.manifest`（原路径 → 新路径 +
冲突检测）。**不要手工 rename**：

- 仅大小写不同的两个文件在 macOS 上无法共存，而 git 在 mac 上通常
  `core.ignorecase=true`，会**静默忽略纯大小写改名** → 必须两步 `git mv a tmp && git mv tmp A`。
- 规范化若牵动 JSON key，需同步验证数据导出工具的逐字节复现约束。

**收尾**：加门禁，发现大写或非 ASCII 路径即报错。

## D-04 平台目标：Windows 发布 + macOS（M4）体验 + Linux 只跑 headless e2e

**状态：已定。**

| 平台 | 角色 | 要求 |
|---|---|---|
| **Windows** | **发布目标** | 单 exe + 资产目录，零运行期依赖（C-7） |
| **macOS / Apple Silicon（M4）** | **用户体验端**（开发期的主要体验机） | 能直接跑；target `aarch64-apple-darwin` |
| Linux / 容器（**可选**） | 只跑 headless 的 e2e 产物，不跑 GUI | 无显示 / 无音频设备（见 D-18） |

**不做**：`.app` bundle、universal2、codesign / notarize、双架构分发（现阶段）。

**代价（反而要求更高）**：mac 会掩盖大小写 bug（D-03 已消灭）；
路径统一 `/`；UTF-8 无 BOM。

**SDL3 在 macOS 的依赖形态 —— 已核实（2026-10-07）**

`sdl3` crate（0.20.x）**默认不启用任何 feature**；自带源码构建与静态链接由这些 feature 提供：

| feature | 行为 |
|---|---|
| `build-from-source` | 从源码编译 SDL3（动态链接） |
| **`build-from-source-static`** | **从源码编译并静态链接** ← 采用这个 |
| `static-link` | 链接**系统已有的**静态 SDL3（仍需先装 SDL3） |
| `use-pkg-config` / `use-vcpkg` | 查找系统库 |
| `link-framework` | macOS Framework 形式的 SDL3 |

⇒ 采用 **`build-from-source-static`**：SDL3 源码随 crate 一起编进我们的二进制，
**C-7「零运行期依赖」在 Mac 上成立**（SDL3 是 zlib 许可，允许静态链接），
也**不需要** `brew install sdl3`。

**构建期**需要的额外工具：C 编译器（macOS 上 Xcode Command Line Tools 自带 clang）
与 **CMake**。⚠️ 这是**构建期**依赖，**不违反 C-7**（C-7 说的是运行期）。
首次编译 SDL3 要几分钟，之后走 cargo 缓存。

**落地验证（2026-10-07，macOS M4 Pro）**：CMake 4.4 + Apple clang 21 构建通过。
另核实：**SDL3 源码由 `sdl3-src` crate 一并下发**（vendored），**不依赖构建期从 GitHub 实时下载**——
即构建只依赖 crates.io（配好镜像即可），无额外网络风险。

**R-9 因此关闭**；D-01 不需要重新审视。

另：macOS 上的**中文输入法**与原版 Windows IME 不等价，属"体感抽查"项，不在 M1 承诺。

## D-05 协议自研，不兼容原版报文

**状态：已定（取代原 `mir2client` 的 D-05「沿用遗留字节协议」）。**

**依据**：两端都在自己手里，不再需要兼容原版客户端；原版报文（6bit 码表、
`#<1-9>…!` 字符帧、`TDefaultMessage` 12B + 16 位 `Series`、Delphi `String[N]`、
`DEFBLOCKSIZE=16`、`*/$S/$R`）没有任何保留价值。

**删除的东西**（连带消灭的坑）：

| 原约束 | 现状 |
|---|---|
| `String[N]` 字节容量、中文 2→3 字节缩水 | **消失** |
| `EqualFold` vs `CompareText` 语义差、名字白名单 | **消失** |
| 排序口径（字节序 ≠ 拼音序） | **消失** |
| `codec.PutShortString` 的 `b[:n]` 切坏多字节 | **消失**（风险点蒸发） |
| `TDefaultMessage.Series` 16 位装不下 `ActorId`、必须坐标优先定位 | **消失** |
| 6bit 码表、`#<1-9>…!` 帧、`DEFBLOCKSIZE`、`*/$S/$R` | **全部删除** |

**代价**：`mir2go` 的 46/46 e2e 与 `mir2cli` **不能直接复用**（它们是围绕遗留协议建的）。
它们转而作为 **mir2go 参照系统自身的回归**，不再服务于新项目。

**新增的最大风险**：见 [protocol.md §9](./protocol.md)——**双实现漂移**。

## D-06 美术"同一套、载体自选"

**状态：已定（放宽自原 `mir2client` 的"原格式直读，不转码"）。**

**依据**：体感一致 ⇒ 必须同一套美术；但**载体属于技术实现，可以自由选**。

原「不转码」的理由是"避免色差与返工"。放宽后必须补一条同等强度的约束：

> **转换必须逐像素可回验**。转换工具必须提供 `verify`：解码产物与原 WIL 逐像素比对一致。
> 没有这条，"体感一致"就没有证据。

载体方案见 [assets.md](./assets.md)，决策见 D-11。

## D-07 渲染：先 CPU 软件合成，后可选换 GPU

**状态：待定。** 推荐先 CPU。

**依据**：原版本来就是软件混合（`DXRender.pas` 8,081 行，含 JIT 代码生成）。
800×600 = 48 万像素，现代 CPU 完全够，且 CPU 合成**行为天然与原版一致**，零 GPU 兼容风险。
先把"走路 + 打怪"跑通，再按实际观感需求局部替换为 SDL3 GPU。

**约束**：渲染接口边界要在 M1 就设计好，保证后续替换不触碰上层。

**⚠️ 附带约束（体感）**：可以提高分辨率，但**视野格数必须锁死**。
原版视距是玩法平衡的一部分，看得更远 = 更容易。

## D-08 排期单位用「验收点/天」

**状态：已定。** 速率基准 **2–3 验收点/天**。

**依据**：行数指标有四个结构性问题：

1. 诱导写"多行但简单"的代码。照搬 70 个手写动画类能刷出 7.6k 行，
   而一个引擎 + 数据表只要 5k 行 —— **前者行数好看，后者才是对的**。
2. **删除不计入产能**。删掉 46k 行 DirectX 包装在行数上是负数。
3. **评审吞吐是隐形上限**。3K 行/天等于零深度评审，缺陷后移，
   在无自动化验收处（手感、时序、遮挡）以 10 倍代价偿还。
4. 对"移植遗留"不成立——搬迁要先读懂 87k 行 Delphi。

## D-09 验收 = 两端契约测试 + 体感抽查

**状态：已定（取代原"以原版对拍为验收标准"）。**

**依据**：协议自研 ⇒ 一致性不再由"原版客户端能否连上"来判定，而由
**生成的两端实现能否互通**来判定。这是质变：

| | 原（对拍原版） | 现（契约测试） |
|---|---|---|
| 判定者 | **人眼**看截图/抓包 | **自动断言** |
| 覆盖 | 抽样 | 全消息 |
| 回归成本 | 每次手工 | CI |
| 不确定性 | 高（R-2 曾是"无限期风险"） | 低 |

**分工**：

- **协议 / 逻辑 / 数值** → 契约测试（CI 门禁）
- **视觉与手感**（遮挡顺序、帧时序、受击反馈） → 仍需体感抽查，
  在 Windows 上跑 `mir2standard` 原版客户端或 `mir2go` 参照系统对比

契约测试的具体形态见 [protocol.md §9](./protocol.md)。

## D-11 资产载体（2026-10-07 **重评**）

**状态：已定（重评）。分而治之：地图转自研容器；美术直读 `.wzl`；音频先直读。**

**为什么重评**：原 D-11 选「自研容器」的**首要理由是"原始 WIL 完全没有压缩 ⇒ 体积约减半"**。
但实测我们的真实素材是 **WZL（每图已 zlib 压缩）**，不是未压缩的 WIL ⇒ **该前提不成立**。
详见 [§0.2](#02--素材找到了wsmir2c2026-10-07)。

**实测（`$WS/mir2c`）**

| 资产 | 体量 | 现状压缩 | 重压缩后 | 可省 |
|---|---:|---|---|---|
| 美术 `.wzl`（106 库 / 252 文件） | **1682.9 MB** | 0.22–0.26（**已 zlib**） | lzma 整块 0.12–0.33 | 再省 **15–45%** |
| 地图 `.map`（770 张） | **253.7 MB** | **1.00（未压缩）** | gzip ≈ 0.06–0.10 | **~230 MB ★最大单项** |
| 音频 `.wav`（777 个） | 199.3 MB | 1.00 | ~0.6–0.8 | 40–80 MB |

单库实测：

| 库 | 原图 | WZL 现状 | zlib-9 整块 | lzma 整块 |
|---|---:|---:|---:|---:|
| `SmTiles` | 655 KB | 0.572 | 0.444 | 0.332 |
| `Prguse` | 23.0 MB | 0.218 | 0.212 | 0.121 |
| `Mon1` | 3.8 MB | 0.233 | 0.220 | 0.197 |
| `Hum` | 52.3 MB | 0.263 | 0.246 | 0.221 |

**★ 关键设计结论**：WZL 已接近 zlib 极限（**整块 zlib 只再省 5–7%**）；
要拿到收益必须"**更强压缩 + 分块 solid**"。
⇒ [assets.md §5](./assets.md) 的 M2PK 草案（`flags bit0 = 每项独立 zlib`）**几乎不产生任何体积收益**，
若继续用自研容器，**必须改成"分块 solid（lzma/zstd）"**。

**决定（分而治之）**

| 资产 | 方案 | 理由 |
|---|---|---|
| **地图** | **转自研容器（M2PK-map，分块 solid）** | 未压缩、收益最大（~230 MB）；地图本就整图加载，不需要细粒度随机访问 |
| **美术 `.wzl`** | **直读**（客户端内置 WZL/WZX 解析） | 已压缩；转换仅再省 15–45%，却要付"转换器 + `verify` + 分块缓存"的全程成本。解析器已破解（[assets.md §3.2b](./assets.md)），Crystal 有参考实现 |
| **音频 `.wav`** | **直读**（先） | 收益中等，等实测再决定是否打包 |

**保留的硬要求**：**地图**转换必须提供 `verify`（D-06）——逐格比对。

**被否掉的两个方案**
- **全量 M2PK（每项独立压缩）**：体积 ≈ 现状，纯亏工具链 ⇒ 否。
- **全量 M2PK（分块 solid）**：美术可再省 ~300 MB，但要换"转换器 + verify + 块缓存 + 素材更新重跑" ⇒
  收益/成本不如直读 ⇒ 否（**保留为日后可选优化**，不影响架构）。

**代价**：客户端内置 ~200 行 WZL/WZX 读取器 —— 可接受。

**落地（2026-10-07）**：地图容器已实现 ⇒ [`internal/m2pk`](../internal/m2pk) + [`tools/m2pk`](../tools/m2pk)。
`$WS/mir2c/map` **770 张 / 253.73 MB → 8.83 MB（比率 0.0347，−96.5%）**，
`verify` **逐字节**回验通过（D-06 硬要求）。

**对上面括注的两处修正**（决策本体不变：地图仍走自研容器）：

1. **"分块 solid" 不值得**。全量 solid 相对"一图一块"只省 **6.5%**（zstd：7.7 → 7.2 MB），
   却让"加载任一张小图"必须解开一整块。⇒ 采用**一图一块**（随机访问、可并行、
   单块损坏不影响全局），差额可接受。
2. **编码器改用 brotli q11，不是 zstd**（详见 [assets.md §5.4](./assets.md)）：
   纯 Go 的 zstd（klauspost）比 libzstd 的高档位**差 56%**，先用它实现时容器是 14.46 MB；
   换 brotli 后 8.83 MB。两端都有成熟**纯**实现（Go `andybalholm/brotli`、Rust `brotli`），
   不引入 cgo / C 依赖（符合 D-21）。

## D-13 连接 / 进程 / 服务器边界

**状态：待定。** 推荐：**客户端单连接；服务端三个逻辑角色；横向扩容靠"多区组 + 无状态 gate"。**

### 0. 先把三个轴拆开

原版把它们绑在一起了，这是复杂度的根源：

| 轴 | 决定因素 | 原版 |
|---|---|---|
| **进程边界** | 故障域、生命周期、**写所有权** | 7 个进程 |
| **连接边界**（客户端几条 TCP） | 鉴权边界、故障切换、网络路径 | 3 条（Login/Sel/RunGate） |
| **服务器边界**（几台机器） | 容量、地域 | 一个区组多台 |

原版把**服务器边界**的需求（一台机器扛不住连接数）**泄漏进了连接边界**（客户端必须换连接），
于是不得不发明 ticket、跨连接会话迁移、三套客户端状态机。

### 1. 账号 DB 与游戏数据分开 —— 必需，但它要求的是"写所有权"，不是"多连接"

规则：

| 数据 | 唯一 writer |
|---|---|
| `accounts` | **只有 `accountsvc`** |
| `characters` | **只有持有该角色租约的 `gamesvr`** |
| `guilds` / 城堡 / 全区共享状态 | 该区组的 `gamesvr`（`mir2go` 已如此） |

为什么必须分开：

1. **同一角色必须被单一进程独占写**，否则两个区组同时改一个角色 = 装备互相覆盖
   （原版的经典 bug 家族）。
2. 账号是**跨区组共享**的（一个账号在多个区组都有角色），所以它的 owner **不能是任何单个
   `gamesvr`**。
3. 生命周期不同：账号库长期持久；游戏内存状态易失，进程随时可重启。

⇒ **进程必须分开、数据必须分离**，但边界是"**写所有权 + 租约**"，与客户端开几条 TCP **无关**。

### 2. "先选后进入" —— 是状态机阶段，不是连接阶段

| 阶段 | 需要什么 | 由谁提供 |
|---|---|---|
| 握手 | 协议版本、能力协商 | 连接的终结者 |
| 认证 | 账号库 | `accountsvc` |
| 列角色 | 该账号在本区组的角色 | `accountsvc` |
| **选角** | **申请角色租约（独占权）** | `accountsvc`（仲裁者） |
| 加载角色档 | 角色档、物品、技能 | `gamesvr` |
| 进世界 | 地图、实体、广播 | `gamesvr` |

**关键**："先选后进入"的本质是"**进入世界之前必须独占该角色**"，原始需求是防双开覆盖。
它要求的是**跨进程的租约仲裁**，**不是**客户端的两条连接。

`mir2go` 已实现过这套：`game_tickets`（一次性票据，不可重放）+ `game_leases`
（主键 `(account, character_name)`：同角色互斥、同账号多角色可并行）。**可原样搬过来。**

### 3. 推荐拓扑

客户端视角：**一条 TCP、一个地址、一个状态机**。

```
客户端（单 TCP，只连"区组地址"）
  → [gate]     无状态：接入 + 4B 分帧字节转发 + 按连接限流 + 连接元数据
  → [gamesvr]  该区组的会话状态机
        ├── 内部 RPC → accountsvc：认证 / 角色列表 / 申请·续租·释放租约
        └── 本地：加载角色档 → 进世界 → 数据面
```

- **`gamesvr` 是客户端的唯一对端**；账号能力走**内部 RPC**（gRPC），
  **`accountsvc` 不对客户端 Listen**。
- 于是：不需要"连接迁移"，也不需要把 ticket 传给客户端
  （租约在 `gamesvr` 内直接申请）。
- 账号库的写天然串行（只有一个 writer）。

**为什么不让 `accountsvc` 直接面对客户端**（原版做法 / 双连接方案）？
那会让"选角完成 → 进入世界"变成**跨连接/跨进程的状态迁移**，必须发明 ticket 机制桥接——
这正是原版复杂度的来源。双连接的收益是故障隔离，代价是客户端两套状态机、两份心跳、
跨连接会话一致性风险。**在这个项目里不值。**

### 4. "选服"怎么办

原版顺序：连 LoginSrv（账号，跨区）→ 服务器列表 → 选服 → 连该区组 → 选角。
**体感保留，但把灵活性放回它该在的层——数据，而不是连接拓扑：**

- **阶段 1（M1–M2，自用）**：区组列表写在客户端配置里（选服界面渲染本地清单）。
- **阶段 2（若要运营）**：加一个**轻量清单服务**（HTTP GET 一份 JSON：区组名/地址/负载/公告），
  客户端启动拉一次。**这是新增一个独立小服务，不改连接模型。**

### 5. 多程序：三个逻辑角色，建议编译成 1 个二进制

- 三个**逻辑角色**要分开：`gate`（无状态转发）、`accountsvc`（账号 + 租约仲裁）、
  `gamesvr`（区组世界）。理由：写所有权不同、生命周期不同、伸缩方式不同。
- 但**不必是三个二进制**。`mir2go` 已证明 `-role` 多角色可行。
  自用场景 `--role=all` 一个进程最省事，上线时按角色拆开。
- **不要把账号能力塞进 `gamesvr`**——那是上帝对象的老路，会让"角色归属"失去唯一仲裁者。

### 6. 多服务器：部署问题，且有一条硬约束

- **硬约束：一个区组 = 一个 `gamesvr` 进程。** MIR2 的世界状态是**全局共享**的
  （同地图的玩家/怪物/广播/掉落都在一个世界模型里）。**不能把一个区组横向拆成多个
  `gamesvr`**（除非做地图分片，而视野/广播/AI 跨地图边界，投入产出极差）。
- 因此"多服务器"只有三种合法形式：
  1. **多区组** → 多 `gamesvr`（天然分片，账号跨区共享）
  2. **`gate` 多实例** → 无状态，前面挂 LB，**客户端地址不变**
     （这才是原版"多 gate"需求的真正归位之处）
  3. **`accountsvc` 单实例**（早期）；压力大时它只是薄 RPC + DB 层，先垂直扩，
     之后按账号 hash 分片
- **容量判断**：一个区组的真实并发在几百到几千连接量级，Go 单进程轻松扛住
  （epoll，每连接几十 KB/s）。所以**早期 1 个 `gate` 进程足够**——多实例是
  "保留能力、不预先支付复杂度"。

### 7. 三条派生硬要求

1. **会话 token 必须独立于 TCP 连接对象**。否则断线重连与"租约宽限"无法实现
   （断开不立即释放租约，超时才释放）。这是单连接方案能否成立的关键。
2. **租约由 `accountsvc` 唯一仲裁**，`gamesvr` 只是申请方 / 续租方 / 释放方。
3. **`gate` 保持无状态**（[D-17](#d-17-gate-不做协议感知)），上面第 6.2 条依赖它。

### 8. 待拍板

1. 接受"`gamesvr` 作为客户端唯一对端 + 账号走内部 RPC"（替代原版 LoginSrv 直接面对客户端）吗？
2. 选服清单：先写客户端配置，还是现在就要那个轻量清单服务？

## D-16 消息类型用 oneof 信封，字段号即消息号

**状态：已定。** 完整论证见 [protocol.md §4.1](./protocol.md)。

**结论**：**不设独立的 `msg_id` 字段**。用 `Envelope.body` 这个 oneof 的**字段号**
同时承担「类型标识」与「线上编号」两个角色（`field 0x0503 → EntityMove`）。

**收益（按重要性排序）**

1. **编译期穷尽性**：加一条消息，两端**所有分发点都会编译报错**，逼你处理。
   `msg_id` + `bytes body` 给不了这个——加了消息忘了处理会静默走 default 分支。
2. 类型与编号**只有一处定义**，重命名类型不会漏改编号。
3. 日志直接打印变体名，不再是数字。
4. 省掉每包 3–5 字节的 `msg_id`。

**三条硬规则**

- 字段号**全局唯一、永不复用**；避开 protobuf 保留区 **19000–19999**
  （我们的 `0x01xx`–`0x0Cxx` 完全避开）。
- `oneof` 无法跨文件扩展 ⇒ **字段列表集中在 `protocol/envelope.proto`**
  （消息体仍按模块拆文件）。这份集中列表即"消息总目录"。
- 收到未知消息时 oneof 的 case **未设置** ⇒ 显式处理 `None`：记数 + 告警 + 忽略，
  **禁止 panic**。

**反向条件**（何时该改回 `msg_id` + `bytes`）：需要 gate 做协议感知转发 /
消息数膨胀到几百上千 / 需要协议层可被外部扩展（oneof 无法从外部扩展，是唯一硬限制）。
后者的逃生舱是在信封里留一个 `Raw { uint32 msg_id; bytes body; }` 变体给 GM 与调试用，
不必推翻整体设计。

## D-17 gate 不做协议感知

**状态：已定。**

**依据**：原版三个 gate（LoginGate / SelGate / RunGate）各自拆包，是为了注入真实 IP、
按消息限流等；代价是 gate 必须**理解协议**，跟着 schema 一起变。

新协议下让 gate 退化成**纯粹的 TCP 接入层**：

- 只做：连接接入、4 字节长度分帧的**字节转发**、按连接限流、连接元数据采集。
- 真实 IP 等信息走**内部 RPC 的 metadata** 传给 `gamesvr`，不塞进协议报文。
- gate **不需要**有 protobuf 依赖。

**收益**

- gate 不随 schema 演进；`oneof` 需要完整 parse 的代价问题在 gate 侧直接消失
  （[protocol.md §4.1](./protocol.md)）。
- 进程划分更简单：gate 可以是无状态的（甚至用现成的 L4 代理思路）。

**代价**

- 按**消息类型**的限流 / 审计 / 黑名单要放到 `gamesvr`（gate 只能按连接与字节量限流）。
  这属于可接受的迁移成本。

## D-18 客户端是**两个产物**，共用同一个 `core`

**状态：已定。**

| 产物 | 形态 | 运行环境 | 依赖 |
|---|---|---|---|
| `client/e2e` | CLI 程序（读剧本 → 断言 → 退出码） | **无显示环境**（Mac 本地 / 容器 / CI 都能跑） | **禁止依赖 SDL3** |
| `client/app` | GUI 程序 | Windows 发布 / macOS M4 体验 | SDL3 |

两者**共用 `client/core`**：协议编解码、会话状态机、资产解码、配置。

### 为什么 e2e 不许依赖 SDL3

1. e2e 必须能在**无显示环境**里跑（容器 / CI）。即便在 Mac 上跑，也**不该为了测试拉起
   窗口与音频设备**——SDL 在无设备时会初始化失败，靠 dummy driver 绕过去是不该依赖的技巧。
2. 少一个原生依赖：构建更稳、CI 更简单、容器镜像更小。
3. **职责边界本来就不同**：e2e 验证协议与逻辑；渲染与手感属于"体感抽查"（D-09）。

### 最重要的一条纪律

> e2e **必须走与 `app` 完全相同的协议编解码与会话状态机**，
> 不允许任何"测试专用捷径"。否则契约测试形同虚设——它检验的就不是真客户端了。

### 可自动化的门禁（CI 里加一条）

```bash
cargo tree -p mir2-e2e | grep -q sdl3 && { echo "e2e 不许依赖 SDL3"; exit 1; }
```

### 产物 1 能在无显示环境里跑的前提

**不依赖美术库**（D-15 的素材至今缺失）。所以：

- e2e 的第一批剧本只覆盖**协议与逻辑**：登录 / 选角 / 进图 / 移动 / 攻击 / 掉落 / 物品 / 聊天。
- 资产解码用**签入仓库的合成测试资源**（体积小、确定性）验证。
- ⇒ e2e **完全不被 D-15 阻塞**，这也是 M1 能在素材到位前推进的原因。

### 已定（2026-10-07）

**Linux 侧产物出两种架构：`linux/amd64` + `linux/arm64`；默认/首选 `linux/amd64`。**

| 产物 | 目标 | 理由 |
|---|---|---|
| `server`（Go） | **amd64 + arm64** | D-21 无 cgo ⇒ 纯交叉编译，两种架构各一条命令，成本几乎为零 |
| `client/e2e`（Linux） | 容器 / CI 内按宿主架构 | 只跑 headless 契约测试，无需双架构 |
| `client/app`（Windows） | `x86_64-pc-windows-gnu` | 见 D-19 |

**默认 `linux/amd64`**：与 `mir2go` 的现有镜像/部署保持一致，避免"本地 arm64 通过、线上 amd64 挂"。

⚠️ 因此**容器里跑 CI 时要显式 `--platform linux/amd64`**（Mac M4 上 Docker 默认是 arm64）。
这同时消除了 [D-20](#d-20-大小写敏感门禁mac-开发特有) 里"CI 门禁架构与部署架构不一致"的隐患。

## D-19 构建矩阵：**全部原生在 macOS 上开发与构建**

**状态：已定。**（取代原"docker 为主构建环境"的写法）

**前提**：主力开发机 = macOS（Apple Silicon / M4），**不再用容器做日常开发**。

| 产物 | **构建** | 运行 |
|---|---|---|
| `server`（Go） | **Mac 原生**（`CGO_ENABLED=0`） | Mac 本地 / Linux 部署（交叉编译产物） |
| `client/e2e`（Rust） | **Mac 原生** | Mac 本地（亦可在容器 / CI 里跑，见 D-18） |
| `client/app`（macOS） | **Mac 原生** | macOS M4 体验 |
| `client/app`（Windows 发布） | **Mac 原生交叉编译**（`x86_64-pc-windows-gnu` + mingw-w64 + CMake） | Windows |

### 为什么 macOS 产物必须在 macOS 上构建

这条即使容器方案不变也成立：

1. macOS 二进制必须链接 **Apple 的 SDK 与系统框架**（libSystem、CoreFoundation、
   Cocoa/Metal——SDL3 在 mac 上要用到）。交叉编译到 `aarch64-apple-darwin`
   需要 macOS SDK 与 `ld64`，Linux 上没有。
2. 唯一绕法是 **`osxcross`**（把 Apple SDK 塞进 Linux 容器），但：
   **Apple SDK 的许可不允许再分发**；每次 SDK 升级都要重搭；
   **Apple Silicon 上任何可执行文件至少要 ad-hoc 签名**，签名要用 Apple 的 `codesign`，
   `osxcross` 做不了这一步，硬做也很脆。
3. 即便勉强跑通，迭代体验极差：改一行要等交叉编译 + 手工签名 + 拷回 Mac。

### 容器 / CI 的角色降级为可选

- 只用于 **① Linux 部署产物的可复现构建 ② CI 门禁**（尤其是大小写敏感检查，见 D-20）。
- 日常开发**不需要**容器：Mac + Go + Rust + CMake 是自足的。

### Mac 上的交叉编译能力（一条命令出目标产物）

```bash
# Linux 部署产物（纯 Go 才这么轻松，见 D-21）
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build ./server/...
# Windows 发布产物
rustup target add x86_64-pc-windows-gnu
```

## D-20 大小写敏感门禁（Mac 开发特有）

**状态：已定。**

**问题**：macOS 文件系统默认**大小写不敏感**。开发机换成 Mac 之后，
"大小写 bug 被掩盖"从理论风险变成 **100% 的日常现实**——
代码里的 import 路径、引用的资源名、`.proto` 文件名，写错了在 Mac 上照样跑，
**部署到 Linux 才炸**。

**这是 [D-03](#d-03-文件名全小写无中文--分隔) 的互补措施**：
D-03（全小写命名）**减少风险面**，D-20 **兜住剩下的**（代码/配置里的引用大小写）。

**对策（组合，全部落实）**

| # | 措施 | 说明 |
|---|---|---|
| 1 | **用大小写敏感的 APFS 卷放工作区** | 推荐，一劳永逸 |
| 2 | **CI 里跑一次 Linux 构建 / 测试** | 最终门禁，无法规避 |
| 3 | 迁移前做冲突自查 | 已实测本工作区 **0 个**冲突 |

**在 Mac 上建大小写敏感卷**

```bash
diskutil list                                        # 先确认盘号
diskutil apfs addVolume disk1 APFSX mir2ws -caseSensitive
```

**冲突自查（在源机器上跑，输出为空即安全）**

```bash
find $WS -not -path '*/.git/*' -printf '%p\n' | tr 'A-Z' 'a-z' | sort | uniq -d
```

⚠️ **git 的陷阱**：大小写不敏感的文件系统上，**纯大小写改名会被 git 静默忽略**
（`core.ignorecase=true`）。必须两步：`git mv a tmp && git mv tmp A`。
D-03 的资产规范化也会踩到这条。

## D-21 禁 cgo（`CGO_ENABLED=0`）

**状态：已定。**

**依据**：`CGO_ENABLED=0` 一次买到三件事：

1. **Mac 上开发、一条命令交叉编译出 Linux 部署产物**——
   `GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build`。有 cgo 就没这么轻松。
2. **静态二进制**：无 glibc 版本耦合，容器基础镜像可以做到极小。
3. **构建可复现**：不依赖宿主机的 C 工具链版本。

**现状**：`mir2go` **已符合**，继承即可——它的
`internal/storage/sqlite/store.go` 开头就写明这个理由，SQLite 用的是
`modernc.org/sqlite`（纯 Go）而不是 `mattn/go-sqlite3`（cgo）。

**规则**：新增依赖**优先选纯 Go 实现**；确实需要 C 库时**先讨论**，
不要默默引入 cgo（它会同时破坏上面三件事）。

## D-22 地图源目录（**已定**）

**状态：已定（2026-10-07）：唯一真源 = `$WS/mir2c/map`（客户端集，770 张）。**

**裁决依据（来自素材所有者）**：客户端自带的 `map/` **来自 SDO（盛大）官方分发，属经典版**；
`$WS/mir2go/data/map` 是参照服务端自行收集的一套，来源与版本都不如客户端集可考。
⇒ 与 **C-1（美术必须与原版一致）** 同源，故**以客户端集为准**。

**事实**：原始地图有**两份**，内容并不一致（实测见 [assets.md §3.3c](./assets.md)）。

| 来源 | 张数 | 体积 | 用途 |
|---|---:|---:|---|
| `$WS/mir2c/map` | **770** `.map` + 1 `.mex` | 253.7 MB | **客户端**自带（assets.md §2 记的就是它） |
| `$WS/mir2go/data/map` | 605 | 242 MB | **参照服务端**自带 |

规范化名字后可配 **557** 对：**552 对逐字节相同，5 对内容不同**：

- `4.map`：客户端 **8.6 MB**（36 B/格）vs 服务端 **2.9 MB**（12 B/格）——**同一张图两种布局**；
- `1.map` / `5.map` / `D2071.map` / `0115.map`：同尺寸但内容不同
  （差异 0.006%–0.18%，落在保留区与少量格上）。

另有客户端独有 **208** 张、服务端独有 **42** 张。

**为什么必须二选一**：客户端渲染与服务端碰撞/门判定必须看**同一份**地图数据，
否则会出现"客户端看得见、服务端说走不过去"这类不一致——这类 bug 极难排查。

**落地要求**

1. **服务端也读客户端集**。地图容器是**唯一通道**（`tools/m2pk/build.sh` 只认 `mir2c/map`），
   所以"客户端看得见、服务端说走不过去"这类不一致在**结构上被消除**，
   而不是靠"记得两边都用同一份"的纪律。
2. **`mir2go` 的地图不参与**。对拍遇到那 5 张差异（[assets.md §3.3c](./assets.md)）时，
   **以本项目为准**，并把它记为"参照系统的已知偏差"，不要反过来改我们。
3. **`build.sh` 不得静默回退到服务端集**：找不到客户端集就**报错退出**——
   静默拿到另一套 = 悄悄换掉了整个游戏世界的地形。
4. **解析器要尽早支持 36 B/格**：客户端集里 **39 张**是这种布局（26.7 MB），
   其中 **`4.map`（8.6 MB）** 是体量最大的核心图之一；不支持的话 M1 一进主城就撞上。

## D-23 真实客户端 IP 如何从 gate 传到后端

**状态：已定（2026-10-07）—— 采用 ① PROXY protocol v1。**

**背景**：这是 [D-17](#d-17-gate-不做协议感知) 的直接后果。旧协议"往登录首帧的文本 token
末尾拼 `|<IP>`"这一手没法照搬 —— 新协议里不再有那种"可以顺手拼一段"的定长串字段
（自研协议的好处之一，见 protocol.md §10），而且那种做法本身就是**客户端自报**。

**为什么需要它**：后端目前不用 IP 做判定，但一旦要做**封禁 / 同 IP 多开限制 /
登录审计 / 反外挂画像**，就必须有一个**不可伪造**的来源。

**决策**：gate 在**连上后端之后、转发任何游戏数据之前**，先写一行 ASCII：

	PROXY TCP4 <源IP> <目的IP> <源端口> <目的端口>\r\n
	PROXY UNKNOWN\r\n                                  ← 拿不到地址时（规格允许）

后端剥掉这一行，之后的字节流**原样不动**。

**为什么是它**

| 方案 | 结论 |
|---|---|
| **① PROXY protocol v1** | **采用**。它是为这件事发明的标准（nginx / Envoy / AWS NLB 通用），且天然满足 D-17：gate 只是写下自己**本来就知道**的东西，完全不必理解游戏协议；后端也不必在 schema 里多一个"只有网关该填"的字段 |
| ② 后端向网关发起内部查询 | 否。多一条内部控制通道，且 gate 从"无状态"变成"有状态"（要维护连接元数据的生命周期） |
| ③ 把 `client_ip` 放进 `ClientHello` | 否。**等于相信客户端自报**（谁都能自称 1.2.3.4），且污染 schema 语义 |

**两条硬规则**（缺一条，这道门就形同虚设）

1. **接入策略只有两种，没有第三种**：要么"必须带头"（缺头即断开），要么"完全不认"。
   「有头就解析、没头退回 socket 地址」是**可伪造**的 —— 能直连到后端的人自己写一行
   `PROXY TCP4 1.2.3.4 …` 就能冒充任意 IP。实现里刻意没有这个中间态（`internal/proxyproto`）。
2. **后端只监听内网/本机**（如 `127.0.0.1:7200`）。第一道门是"外部根本连不到后端"，
   头校验是第二道 —— 别把全部希望押在头校验上。

**落地**

| 位置 | 做什么 |
|---|---|
| `server/internal/proxyproto` | v1 的读写两端（`WriteV1` / `ServerConn`）：严格校验、限长 107 字节、等头有超时（读完即清，不留给协议读）、认出 v2 魔数并明确报错；头之后的字节经缓冲包装后**一字节不少** |
| `server/cmd/gate` | 每条上游连接先写头（`-proxy-protocol`，**默认开**）。对端不认识该头时关掉（例：把网关挡在参照系统 `mir2go` 前面做对拍） |
| `server/cmd/gamesvr`、`server/cmd/accountsvc` | `-proxy-protocol`（**默认关** = 直连调试）：打开后**要求**头，缺头即断开；真实地址用于 AdminList 匹配与全部日志 |

⚠️ **默认值刻意不对称**：gate 默认开（一个不说明"背后是谁"的网关没有意义），
后端默认关（默认拓扑就是直连 —— `mir2cli` 与客户端回归都直接连 `:7200`）。
把 gate 摆到前面时，后端的这一项**必须**跟着打开，否则所有连接看起来都来自网关自己
（启动日志会明确打印当前来源，见两处的 `客户端地址来源:` 一行）。

**顺带删掉的东西**：`wire.LoginToken` 的 `ClientIP` 字段与 `<idx>|<IP>` 解析已删除 ——
它既是"客户端自报"，又与 PROXY 头构成**两个真相来源**（而且客户端可以覆盖网关给的值）。

**反悔条件**：若将来需要 **UDP** 或 gate 与后端**跨进程**共享连接元数据，
那是走 v2 二进制头（`internal/proxyproto` 已能认出并给出明确报错），而不是换方案。
